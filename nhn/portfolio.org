역량·성과 기술서가 개인지식관리에서 조직의 에이전트 작업면까지 이어 온 방향을 설명했다면, 이 포트폴리오는 그 방향이 실제 프로젝트에서 어떻게 작동했는지 보여줍니다. 다섯 프로젝트를 같은 질문으로 읽습니다 — *어떤 문제가 있었고, 어디까지 소유했으며, 어떤 경계를 그었고, 운영 후 무엇이 달라졌고, 다음 사람은 어디서 이어받는가.*

순서는 회사 도메인에 착지한 읽기 전용 에이전트 접점에서 시작해, 에이전트 런타임 운영·기억 계층·하네스 디스패치와 공유 작업면을 거쳐, 그 아래의 Embedded Linux·Backend·제품 기반으로 내려갑니다. 사내 수행 사실에는 =[사내]=, 공개 확인 지점에는 =[공개]= 라벨을 붙입니다. 공개할 수 없는 코드를 억지 근거로 바꾸지 않고, 설계 판단과 공개 저장소·PR·기록을 나란히 둡니다.

- *보조 인프라* — 문서 임베딩과 리랭킹을 GPU·컨테이너 위에서 서빙하고, PostgreSQL·pgvector를 검색 접점으로 사용합니다 [사내] [cite:@pgvector]. 이 계층은 프로젝트의 주인공이 아니라 두 도메인 에이전트가 근거를 회수하도록 받치는 기반입니다.

*핵심 판단 ① — 권한보다 먼저 경계를 그었습니다.* 자격증명은 에이전트가 취급하지 않고, 변경·실행 경로는 기본적으로 차단합니다. 원시 개인정보는 표준입력 경계로만 흐르고 문서·세션·커밋에 남기지 않습니다. *자연어를 실데이터로 잇되 읽기 전용 경계를 넘지 않습니다.*

*핵심 판단 ② — 새 화면보다 담당자의 기존 작업면을 택했습니다.* 별도 대시보드 제품을 만드는 대신 운영팀이 이미 읽는 Markdown과 메신저에 결과와 근거 링크를 놓았습니다.

*운영 후 상태 변화.* 운영팀은 상담 질문을 도메인 에이전트에 맡기고 개별 근거까지 되짚을 수 있게 됐습니다. 누적 상담 원자료와 판독 표면은 운영자·봇 워크스페이스가 같은 계약으로 소비합니다 [운영 기록].

*인계·문서.* 운영팀의 반복되는 고통을 듣고 → 요구를 계약으로 번역하고 → 경계를 합의하고 → 워크벤치를 제공하고 → 피드백을 다시 데이터·문서·이슈로 되돌리는 루프를 만들었습니다.

*확인 지점.* [사내·비공개] voscli·incidentcli 운영 · [공개] 같은 검색·기억 계층의 구현 andenken [cite:@repo-andenken] · pgvector [cite:@pgvector].

*한 줄 명제.* *대화 기억을 특정 런타임에서 떼어 여러 하네스가 소비할 수 있는 독립 검색 계층으로 만들었습니다.*

*핵심 판단 ① — 검색 알고리즘보다 기억의 소유 경계를 먼저 나눴습니다.* 세션과 공개 지식베이스를 별도 트랙으로 인덱싱하고, LanceDB [cite:@lancedb] 위에서 벡터와 전문검색(BM25 [cite:@bm25-robertson]) 점수를 정규화해 합칩니다. 한↔영 질의 확장과 회수 추적은 별도 도구로 분리했습니다.

*핵심 판단 ② — 구현과 로드맵을 같은 무게로 주장하지 않습니다.* 현재 운영되는 것은 임베딩·검색 축입니다. 답변 전 차단형 active recall은 하네스가 소비하는 경계이고, 야간 증류는 아직 별도 로드맵입니다.

*운영 후 상태 변화.* 세션과 가든 두 트랙이 라이브로 인덱싱·검색되고, 에이전트가 과거 대화와 공개 지식을 같은 질의에서 회수합니다. 이 계층은 프로젝트 1의 사내 임베딩·리랭킹 운영과 같은 설계 감각을 공개 코드로 확인하게 합니다.

*인계·문서.* 인덱싱과 검색 표면을 CLI·에이전트 스킬로 분리해 다른 하네스가 같은 백엔드를 소비할 수 있게 했습니다.

*확인 지점.* [공개] andenken [cite:@repo-andenken] · Qwen3-Embedding [cite:@qwen3-embedding] · LanceDB [cite:@lancedb].
