역량·성과 기술서가 개인지식관리에서 조직의 에이전트 작업면까지 이어 온 방향을 설명했다면, 이 포트폴리오는 그 방향이 실제 프로젝트에서 어떻게 작동했는지 보여줍니다. 다섯 프로젝트를 같은 질문으로 읽습니다 — *어떤 문제가 있었고, 어디까지 소유했으며, 어떤 경계를 그었고, 운영 후 무엇이 달라졌고, 다음 사람은 어디서 이어받는가.*

아래 다섯 프로젝트는 서로 다른 자리에서 하나의 축 — *조직이 이어받을 수 있는 에이전트 운영 기반* — 을 증명하고, 각기 공고의 다른 요건에 대응합니다. 회사 도메인에 착지한 읽기 전용 접점에서 시작해, 런타임 운영·기억 계층·프로토콜 협업을 거쳐, 그 아래의 Embedded Linux·Backend·제품 기반으로 내려갑니다.

|---+----------+-------------+-----------|

/기간 2025–현재 · 소유 범위 접점 설계·구현·운영 · 협업면 운영·QA·제품·개발 조직 · 스택 Clojure, Python, GPU·컨테이너, PostgreSQL·pgvector, Kafka, AWS·Oracle Cloud/

*한 줄 명제.* *기존 IoT·상담·운영 시스템을 교체하지 않고, 읽기 전용·증거 우선의 에이전트 접점을 붙였습니다.*

*맥락과 문제.* 스마트홈 IoT 플랫폼은 이미 고객과 운영 조직이 사용하는 여러 시스템 위에서 돌아갑니다. 여기서 AX 전환은 새 대시보드를 하나 더 만드는 일이 아니었습니다. 도메인의 주인이 자기 언어로 묻되, 에이전트의 답을 원자료까지 되짚을 수 있어야 했습니다.

*소유 범위와 협업면.* 업무 데이터 접점과 도메인 CLI의 설계·구현·운영을 맡았습니다. 운영팀의 질문을 개발 가능한 계약으로 번역하고, 제품·개발 조직과 개인정보·권한·원천 시스템의 경계를 합의했습니다.

- =voscli= 프로젝트 [사내] — 「무엇이 얼마나 일어났는가」를 맡습니다. VOC·상담 데이터의 기간·단위·포함 정책을 고정해 집계가 질문마다 흔들리지 않게 하고, 집계 결과의 판단 근거를 개별 상담까지 역추적합니다. 평소와 다른 신호를 검출하는 일도 이 계약 위에서 합니다.
- =incidentcli= 프로젝트 [사내] — 「언제 무슨 순서로 일어났는가」를 맡습니다. 운영 장애·VOC·디바이스 로그·런타임 데이터를 하나의 KST 시간축으로 회수·정렬합니다. 외부 호출은 읽기 전용이고 덤프를 쌓지 않으며, 수집과 인시던트 기록은 검증 계약을 통과해야 다음 단계로 갑니다.
- *보조 인프라* — 문서 임베딩과 리랭킹을 GPU·컨테이너 위에서 서빙하고, PostgreSQL·pgvector를 검색 접점으로 사용합니다 [사내] [cite:@pgvector]. 이 계층은 프로젝트의 주인공이 아니라 두 도메인 에이전트가 근거를 회수하도록 받치는 기반입니다.

*핵심 판단 ① — 권한보다 먼저 경계를 그었습니다.* 자격증명은 에이전트가 취급하지 않고, 변경·실행 경로는 기본적으로 차단합니다. 원시 개인정보는 표준입력 경계로만 흐르고 문서·세션·커밋에 남기지 않습니다. *자연어를 실데이터로 잇되 읽기 전용 경계를 넘지 않습니다.*

*핵심 판단 ② — 새 화면보다 담당자의 기존 작업면을 택했습니다.* 별도 대시보드 제품을 만드는 대신 운영팀이 이미 읽는 Markdown과 메신저에 결과와 근거 링크를 놓았습니다.

*운영 후 상태 변화.* 운영팀은 상담 질문을 도메인 에이전트에 맡기고 개별 근거까지 되짚을 수 있게 됐습니다. 누적 상담 원자료와 판독 표면은 운영자·봇 워크스페이스가 같은 계약으로 소비합니다 [운영 기록].

*인계·문서.* 운영팀의 반복되는 고통을 듣고 → 요구를 계약으로 번역하고 → 경계를 합의하고 → 워크벤치를 제공하고 → 피드백을 다시 데이터·문서·이슈로 되돌리는 루프를 만들었습니다.

*확인 지점.* [사내·비공개] voscli·incidentcli 운영 · [공개] 같은 검색·기억 계층의 구현 andenken [cite:@repo-andenken] · pgvector [cite:@pgvector].
