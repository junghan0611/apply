# AGENTS.md — applications/ (지원 실행 · 제출 기록 레인)

이 디렉터리는 문서를 **만드는** 곳이 아니라 **내는** 곳이다. 만드는 곳은 둘이다.

| 레인 | 위치 | 성격 |
|---|---|---|
| 조준 제출본 | `../nhn/` | 공고 하나에 조준한 3종 세트 (닫힘) |
| 이력서 발사대 | `../resume/` | 공통 프레임 → 타깃별 컷 6종 |
| **지원 실행·기록** | **`.` (여기)** | **어디에 · 언제 · 무엇을 냈는가** |

여기의 목적은 하나다. **"어디 냈는지 모르는 상태"를 만들지 않는다.** 하루에 열 곳을 내면
2주 뒤 연락이 왔을 때 어느 공고인지 모른다. 공고는 마감되면 사라진다. 그래서 낼 때 남긴다.

## 원장(LEDGER)이 SSOT다

`LEDGER.md` 한 장이 전체 지원 이력이다. 건마다 폴더가 하나 생기고, 원장에 행이 하나 는다.

```
applications/
  LEDGER.md               ← 전체 지원 이력 (SSOT)
  FAQ.md                  ← 폼·면접 답변 사전 — 값 + 근거 + 화법 (폼 채울 때 여기서 가져온다)
  INBOX.md                ← 후보 대기열 + 지원 경로(플랫폼별) 확인 결과
  new.sh                  ← 건 생성 + 원장 행 추가
  <company>--<role>/
    JD.md                 ← 공고 스냅샷 (공고는 사라진다. 낼 때 떠 둔다)
    submission.md         ← 무엇을·언제·어떻게 냈는지 + 답한 질문과 답
    submit/               ← 그 폼에 실제로 올린 파일 사본
    (필요시) cover-letter.md · pre-question.md · build.sh
  _archive/               ← 마감·불합격 건 (원장 행은 남긴다)
```

### `submit/` — 건마다 사본을 둔다

**제출지마다 내라는 것이 다르다.** 어디는 영문 이력서 한 장, 어디는 국문 자기소개서, 어디는
사전질문 서술형, 어디는 경력기술서를 따로 받는다. `resume/build/` 는 **베이스 발사대**이고,
건마다 무엇을 올렸는지는 **그 폴더의 `submit/` 이 증언한다.**

- `resume/build/` 를 가리키는 링크로 두지 않는다. **사본을 둔다.** 발사대는 계속 갱신되므로
  링크만 두면 3개월 뒤 「그때 무엇을 냈는지」가 사라진다.
- 그 건에만 필요한 문서(국문 자기소개서, 사전질문 답변)는 **그 폴더에서 만든다.**
  `resume/` 를 오염시키지 않는다.
- 폴더에 `build.sh` 를 두어 **제출 직전에 한 번 돌려 최신 컷을 다시 복사**하게 한다.
  발사대가 그 사이에 갱신됐을 수 있다.
- `submit/` 은 git 으로 추적한다. 용량은 건당 100~200KB 수준이고, **무엇을 냈는지가 이
  저장소의 존재 이유다.**

**폴더 이름은 `<company>--<role>`이고 전부 영문 소문자 하이픈이다.** 한글 폴더명을 만들지
않는다 — 외부 ATS 업로드·zip·CI 어디서든 깨지지 않아야 하고, 경로를 눈으로 훑을 때 영문 한
벌이 읽기 쉽다. 한글 표기는 `JD.md` 안에 남는다. `new.sh`는 한글만 들어오면 슬러그가 비어
**멈추고 영문을 요구한다.**

날짜는 폴더명에 넣지 않는다 — 같은 회사에 다시 낼 때 헷갈린다. 날짜는 원장과
`submission.md`에 있다.

## 타깃 기준 (2026-07-28 GLG 확정)

「낼 곳」을 추리는 레인과 「낼 글」을 쓰는 이 레인이 같은 기준을 쓴다. 기준에 어긋나는 건이
들어오면 **글을 쓰기 전에 그 사실을 먼저 말한다.**

| 축 | 기준 |
|---|---|
| 지역 | **성남(판교 포함) · 강남권.** 수원 거주 기준 통근 가능 범위 |
| 규모 | **영세 스타트업 제외.** 시리즈 이전·소수 인원 조직은 거른다 |
| 경로 | **큰 기업은 자체 채용 사이트에서 낸다.** LinkedIn Easy Apply로 안 끝난다 |
| 직무 | 한 회사에 여러 공고가 열려 있으면 **전부 내지 않는다.** 아래 §직무 선택 |

### 한 회사에 공고가 여러 개일 때 — 기본은 하나, 예외는 사람이 결정

같은 회사에 다섯 축(SWE · AI · FDE · Embedded · DevEx) 중 둘 이상이 열려 있는 경우가 많다.
기본은 **하나만 고르는 것**이다. 다만 이것은 에이전트의 전략 권고이지 금지 규칙이 아니다.
GLG가 서로 다른 증거 패키지를 읽고 복수 지원을 명시하면 그대로 진행하고, 왜 예외로 갔는지
각 `submission.md`에 남긴다. 기본 선택 기준:

1. **증거가 가장 두꺼운 축**을 고른다 — 서류가 이길 수 있는 자리.
2. 증거가 비슷하면 **경쟁이 얕은 축**을 고른다 (FDE·Embedded·DevEx는 AI Engineer보다 지원자가 적다).
3. 그래도 남으면 **JD가 문서·전파·협업을 요구하는 쪽**을 고른다 — GLG의 차별점이 거기 있다.
4. 고르고 나면 **왜 그 직무였는지를 `submission.md`에 한 줄로 남긴다.** 나중에 같은 회사에
   다시 낼 때 이 기록이 근거가 된다.

NHN 건이 이 방식이었다 — 공고 제목은 「AI 인프라(백엔드)」였지만 주요 업무 절반이 문서·교육
이라 **빌드 + 전파의 이중 직무**로 읽고 거기에 조준했다(`../nhn/AGENTS.md`).

## 건 하나 내는 순서

```bash
./new.sh "회사명" "직무명" "공고URL"     # 폴더 + 템플릿 + 원장 행
```

0. **기존 파일을 먼저 읽는다.** 이미 있는 `JD.md`·`submission.md`·`FAQ.md`를 읽지 않고
   `write`하지 않는다. 병렬 레인이 만든 내용을 지우지 말고 `edit`로 상태를 이어간다.
1. **`new.sh`로 자리를 먼저 만든다.** 내고 나서 기록하려 하면 안 남는다.
2. **공고 본문을 `JD.md`에 떠 둔다.** 브라우저에서 읽은 원문을 그대로. 요약하지 않는다 —
   면접 준비 때 원문이 필요하다.
3. **컷을 고른다.** `../resume/build/` 의 6종 중 하나. 다섯 축으로 안 덮이면
   `../resume/AGENTS.md` §「새 타깃 컷 만드는 법」으로 5분에 하나 뽑는다.
4. **폼을 채운다.** 반복 질문은 `FAQ.md`에서 가져온다. 사전에 없는 질문이 나오면
   답을 정한 뒤 **`FAQ.md`에 추가한다** — 그 질문은 반드시 다시 나온다.
5. **제출은 GLG가 승인한다.** 아래 §경계.
6. GLG가 제출 완료를 알리면 즉시 **두 곳을 함께 닫는다**.
   - `LEDGER.md`: `submitted` + 지원일
   - 해당 `submission.md`: `submitted` + 실제 업로드 사본 + 완료 기록
   개인 필드 값은 적지 않고 “GLG가 브라우저에서 완료, 값 미보존”으로 남긴다.
7. `./check.py`가 통과하기 전에는 제출 판을 끝났다고 보고하거나 커밋하지 않는다.

## 브라우저 워크플로 — 검증된 사실 (2026-07-28)

에이전트가 크롬으로 실제 확인한 것만 적는다.

### LinkedIn 원클릭 지원(Easy Apply) — 5단계

| 단계 | 내용 | 자동화 |
|---|---|---|
| 1/5 | Contact info — 이름·이메일·국가코드·휴대폰 | 프로필에서 자동 채워짐 |
| 2/5 | Resume — 저장된 이력서 선택 또는 업로드 (2MB 미만, DOC/DOCX/PDF) | 선택 가능 |
| 3/5 | 프리미엄 「1지망으로 표시」 (월 3개) | **GLG 전략 판단** |
| 4/5 | Additional Questions — 공고별 (연차·학위·비자 등) | `FAQ.md` |
| 5/5 | 검토 → **제출** | **GLG 승인 필요** |

- 모달을 닫으면 「저장 / 삭제」를 묻는다. **저장하면 제출되지 않고 「계속」으로 남는다** —
  후보를 열어만 두고 나중에 마저 낼 때 쓴다. 업로드한 파일은 저장되지 않는다.
- 저장된 이력서는 `linkedin.com/jobs/application-settings/` 에서 관리한다.
  **여기 올려 둔 파일이 모든 Easy Apply의 기본 선택이 된다.** 한 공고용 문서를 올려 두면
  다음 열 곳에 그게 딸려 나간다.
- `file_upload` 도구가 **이 저장소 경로를 그대로 받는다.** 검증:
  `resume/build/KimJunghan_Resume.pdf` 업로드 성공(39KB). 파일 선택 대화상자를 열지 않는다.

### 목록 수집

검색 결과는 가상 목록이라 스크롤한 만큼만 DOM에 있다. `li[data-occludable-job-id]` 로
id·제목·회사·원클릭 여부를 뽑을 수 있다. 같은 카드가 `li`와 `div` 양쪽에 잡히므로 id로 중복을 턴다.

### 외부 ATS

「회사 웹사이트에서 지원」은 새 탭으로 튕긴다(greetinghr·wanted·saramin·잡코리아·Greenhouse 등).
폼 구조가 제각각이라 건마다 읽어야 한다. **처음 보는 ATS를 만나면 그 구조를 이 절에 추가한다.**

## 경계 — 에이전트가 넘지 않는 선

- **제출(Submit·지원하기·최종 확인) 버튼은 GLG의 명시 승인 없이 누르지 않는다.** 세션마다,
  건마다 따로 받는다. 한 건의 승인이 다음 건으로 이어지지 않는다.
- **계정 설정·프로필을 임의로 바꾸지 않는다.** 저장된 이력서 교체처럼 워크플로에 필요한
  변경은 GLG에게 알린 뒤 한다.
- **답을 지어내지 않는다.** 연차·비자·희망연봉·입사가능일은 `FAQ.md`에 GLG가 확정한
  값만 쓴다. 사전에 없으면 **묻는다.** 폼을 비워 두는 편이 틀린 값을 넣는 것보다 낫다.
  민감한 법적 값은 브라우저에서만 확정하고 Git에는 처리 규칙만 남겨도 된다.
- **개인정보를 원장에 적지 않는다.** 주민번호·계좌·비밀번호는 어떤 폼에도 에이전트가
  넣지 않는다 — GLG가 직접 입력한다.
- 회사명·지원 경로는 이 저장소(PRIVATE)에 남기되, **공개 트랙(`junghan0611/*`)으로
  자동 동기화하지 않는다.**
