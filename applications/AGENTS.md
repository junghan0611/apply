# AGENTS.md — applications/ (지원 실행 · 제출 기록 레인)

이 디렉터리는 문서를 **만드는** 곳이 아니라 **내는** 곳이다. 만드는 곳은 둘이다.

| 레인 | 위치 | 성격 |
|---|---|---|
| **dossier 발사대** | `../dossier/` | 한 건에 조준한 두꺼운 3종 세트 — **깊이 축** |
| 이력서 발사대 | `../resume/` | 공통 프레임 → 타깃별 컷 6종 |
| **지원 실행·기록** | **`.` (여기)** | **어디에 · 언제 · 무엇을 냈는가** — **넓이 축** |

> **지금은 넓이 축이다** (2026-07-29 GLG). 이 레인의 방향은 **여러 곳의 제출 플랫폼을 갖추는
> 것**이고, 다 갖춰지면 `../dossier/` 의 깊이 축으로 넘어간다. 낼 곳이 갖춰지기 전에 문서
> 깊이를 파지 않는다.

여기의 목적은 하나다. **"어디 냈는지 모르는 상태"를 만들지 않는다.** 하루에 열 곳을 내면
2주 뒤 연락이 왔을 때 어느 공고인지 모른다. 공고는 마감되면 사라진다. 그래서 낼 때 남긴다.

## 원장(LEDGER)이 SSOT다

`LEDGER.md` 한 장이 전체 지원 이력이다. 건마다 폴더가 하나 생기고, 원장에 행이 하나 는다.

```
applications/
  LEDGER.md               ← 전체 지원 이력 (SSOT)
  FAQ.md                  ← 폼·면접 답변 사전 — 값 + 근거 + 화법 (폼 채울 때 여기서 가져온다)
  INBOX.md                ← 후보 대기열 + 지원 경로(플랫폼별) 확인 결과
  new.sh                  ← 건 생성 + 원장 행 추가
  <company>--<role>/
    JD.md                 ← 공고 스냅샷 (공고는 사라진다. 낼 때 떠 둔다)
    submission.md         ← 무엇을·언제·어떻게 냈는지 + 답한 질문과 답
    submit/               ← 그 폼에 실제로 올린 파일 사본
    (필요시) cover-letter.md · pre-question.md · referral.md · build.sh
  _archive/               ← 마감·불합격 건 (원장 행은 남긴다)
```

**선택 슬롯은 이름이 정해져 있다.** 같은 것을 매번 다른 파일명으로 만들지 않는다.

| 파일 | 언제 | 무엇이 들어가는가 |
|---|---|---|
| `cover-letter.md` | 폼에 자유서술 칸이나 커버레터 첨부가 있을 때 | **붙여넣을 본문**과 왜 그렇게 썼는지 |
| `pre-question.md` | 사전질문 서술형이 여러 개일 때 | 문항별 답과 글자수 |
| **`referral.md`** | **추천으로 들어갈 때** | 추천 경로·추천인·관계, 추천서 원문, **추천서 주장 ↔ 서류 증거 대조표** |
| `build.sh` | 첨부를 조립해야 할 때 | 제출 직전 한 번 돌려 최신 컷을 `submit/` 로 복사 |

**`referral.md` 는 다시 나온다** (2026-07-29 GLG: *"추천 또 받거나, 다른 지인한테 받을 수도
있다"*). 규칙은 `nhn--ax-transformation-ai-infra/referral.md` §규칙이 정본이다 —
**추천서를 서류 본문에 인용하지 않는다.** 추천은 추천인의 문장이고 서류는 내 문장이다.
추천인 실명은 이 저장소(PRIVATE)에만 두고 제출 문서 본문에 넣지 않는다.

### 검수는 소스가 아니라 제출 세트 위에서 한다 (2026-07-29 GLG)

**GLG 는 org/md 를 읽지 않는다. 그 업체에 올라갈 파일 세트를 그대로 연다.**

```bash
./stage.py            # ready 인 건 전부 세트를 다시 깐다
./stage.py holiday    # 한 건만
```

`stage.py` 가 각 건 `submit/` 에 **나갈 물건 전부**를 깐다 — `submission.md` §첨부 컷에서
읽은 이력서 컷, `cover-letter.md` §붙여넣을 본문을 뽑은 `cover-letter.txt`(폼이 textarea 다),
그리고 `README.md`(어느 파일이 폼의 어느 칸인지) + `MANIFEST.sha256`.

- **수정 요청이 오면 `submit/` 을 손으로 고치지 않는다.** `resume/body.org` · `targets/*.org` ·
  `dossier/*.org` · `cover-letter.md` 를 고치고 **빌드 → `./stage.py`** 로 세트를 다시 깐다.
  세트 단위로 움직여야 제출본과 소스가 갈라지지 않는다.
- **`submitted` 인 건은 `stage.py` 가 건드리지 않는다.** 그때 나간 파일이 사실이다.
- 이력서·dossier 를 재빌드했으면 **`./stage.py` 를 반드시 뒤따라 돌린다.** 안 그러면
  세트가 옛 판이다.

### `submit/` — 건마다 사본을 둔다

**제출지마다 내라는 것이 다르다.** 어디는 영문 이력서 한 장, 어디는 국문 자기소개서, 어디는
사전질문 서술형, 어디는 경력기술서를 따로 받는다. `resume/build/` 는 **베이스 발사대**이고,
건마다 무엇을 올렸는지는 **그 폴더의 `submit/` 이 증언한다.**

- `resume/build/` 를 가리키는 링크로 두지 않는다. **사본을 둔다.** 발사대는 계속 갱신되므로
  링크만 두면 3개월 뒤 「그때 무엇을 냈는지」가 사라진다.
- 그 건에만 필요한 문서(국문 자기소개서, 사전질문 답변)는 **그 폴더에서 만든다.**
  `resume/` 를 오염시키지 않는다.
- 폴더에 `build.sh` 를 두어 **제출 직전에 한 번 돌려 최신 컷을 다시 복사**하게 한다.
  발사대가 그 사이에 갱신됐을 수 있다.
- `submit/` 은 git 으로 추적한다. 이력서 컷만 내는 건은 100~200KB 수준이고, dossier 를 내는
  건은 몇 MB 가 된다. **무엇을 냈는지가 이 저장소의 존재 이유다.**
- **발사대의 `build/` 가 gitignore 라는 이유로 `submit/` 을 비워 두지 않는다.** NHN AX 건이
  2026-07-29 까지 그 상태였다 — 낸 파일이 git 에 없었다. 발사대는 무시해도 되지만
  **사본은 반드시 커밋한다.**
- **10MB 넘는 첨부(증거 패키지 ZIP 등)는 해시로 대신할 수 있다.** 단 조건이 둘이다:
  ① 그 내용물이 이 저장소에 이미 추적되고 있을 것, ② `submit/MANIFEST.sha256` 에 해시를
  남길 것. 조건을 못 채우면 용량이 커도 파일을 넣는다.

**폴더 이름은 `<company>--<role>`이고 전부 영문 소문자 하이픈이다.** 한글 폴더명을 만들지
않는다 — 외부 ATS 업로드·zip·CI 어디서든 깨지지 않아야 하고, 경로를 눈으로 훑을 때 영문 한
벌이 읽기 쉽다. 한글 표기는 `JD.md` 안에 남는다. `new.sh`는 한글만 들어오면 슬러그가 비어
**멈추고 영문을 요구한다.**

날짜는 폴더명에 넣지 않는다 — 같은 회사에 다시 낼 때 헷갈린다. 날짜는 원장과
`submission.md`에 있다.

### `JD.md` — 요약이 아니라 출처가 있는 원문

공고는 다음 순서로 원본을 찾는다.

1. 회사 공식 채용 보드와 원본 ATS;
2. LinkedIn 정식 공고;
3. LinkedIn 개인 채용 포스트;
4. Wanted·Remember·사람인·잡코리아 등 폐쇄 채널의 흔적;
5. 검색 캐시·회사 팀 글.

뒤쪽 출처에서 제목이나 흔적만 찾았으면 그것을 전문처럼 늘리지 않는다. `JD.md` 상단에는 최소한
**확인한 URL · 확인일 · 원본 ATS 여부 · 현재 열림 여부 · 본문 전문/일부/미확인**을 보이게 둔다.
LinkedIn에서 원본 ATS로 옮겨 갔다면 두 URL의 동일 공고 근거도 남긴다.

`JD.md` 본문은 면접 때 다시 인용할 수 있는 원문이어야 한다. 요약·적합도·추천 이유·경계는
`submission.md`가 쥔다. 원문을 못 얻었다면 `본문 미확인`이 값이고, 닫힌 플랫폼의 검색 흔적만으로
요건을 완성하거나 `ready`로 올리지 않는다.

### `ready`의 뜻

`ready`는 “PDF 하나가 있다”가 아니라 **노트북에서 새 문서 작업 없이 검토·개인값 입력·업로드·
Submit만 하면 되는 상태**다. 다음이 한 건의 `submission.md`에 보여야 한다.

- 현재 열려 있는 정확한 공고와 지원 URL;
- 보존한 JD 원문과 출처 수준;
- 필수요건·고용형태·근무지·언어·비자에서 확인한 것과 미확인인 것;
- 왜 이 회사의 이 직무를 골랐는지와 정면 증거·하드 갭;
- 붙일 이력서 컷과 필요한 추가 서류, 재현 가능한 빌드 경로;
- 공개 상태에서 확인 가능한 폼 문항·서류 슬롯;
- 로그인 뒤에만 확인할 조건부 질문과 GLG가 결정할 값;
- **아직 제출하지 않았음**.

브라우저에서만 보이는 질문이 남았다는 이유만으로 `ready`를 금지하지 않는다. 다만 무엇이
브라우저 확인 항목인지 명시되어 있고, 그것을 제외한 문서 작업이 끝나 있어야 한다. 운영상 보류는
원장의 사실 상태를 거짓으로 바꾸지 말고 `NEXT.md`와 해당 `submission.md`에 이유를 남긴다.

### 한 회사에 공고가 여러 개일 때 — 기본은 하나, 예외는 사람이 결정

같은 회사에 다섯 축(SWE · AI · FDE · Embedded · DevEx) 중 둘 이상이 열려 있는 경우가 많다.
기본은 **하나만 고르는 것**이다. 다만 이것은 에이전트의 전략 권고이지 금지 규칙이 아니다.
GLG가 서로 다른 증거 패키지를 읽고 복수 지원을 명시하면 그대로 진행하고, 왜 예외로 갔는지
각 `submission.md`에 남긴다. 기본 선택 기준:

1. **증거가 가장 두꺼운 축**을 고른다 — 서류가 이길 수 있는 자리.
2. 증거가 비슷하면 **경쟁이 얕은 축**을 고른다 (FDE·Embedded·DevEx는 AI Engineer보다 지원자가 적다).
3. 그래도 남으면 **JD가 문서·전파·협업을 요구하는 쪽**을 고른다 — GLG의 차별점이 거기 있다.
4. 고르고 나면 **왜 그 직무였는지를 `submission.md`에 한 줄로 남긴다.** 나중에 같은 회사에
   다시 낼 때 이 기록이 근거가 된다.

NHN 건이 이 방식이었다 — 공고 제목은 「AI 인프라(백엔드)」였지만 주요 업무 절반이 문서·교육
이라 **빌드 + 전파의 이중 직무**로 읽고 거기에 조준했다(`../dossier/AGENTS.md`).

## 건 하나 내는 순서

```bash
./new.sh "회사명" "직무명" "공고URL"     # 폴더 + 템플릿 + 원장 행
```

0. **기존 파일을 먼저 읽는다.** 이미 있는 `JD.md`·`submission.md`·`FAQ.md`를 읽지 않고
   `write`하지 않는다. 병렬 레인이 만든 내용을 지우지 말고 `edit`로 상태를 이어간다.
1. **`new.sh`로 자리를 먼저 만든다.** 내고 나서 기록하려 하면 안 남는다.
2. **공고 본문을 `JD.md`에 떠 둔다.** 공식 ATS/API/브라우저에서 읽은 원문과 출처 수준을
   그대로 둔다. 요약하지 않는다 — 면접 준비 때 원문이 필요하다.
3. **컷을 고른다.** `../resume/build/` 의 6종 중 하나. 다섯 축으로 안 덮이면
   `../resume/AGENTS.md` §「새 타깃 컷 만드는 법」으로 5분에 하나 뽑는다.
4. **공개 폼 스키마를 먼저 읽고 준비한다.** 반복 질문은 `FAQ.md`에서 가져온다. 사전에 없는 질문이 나오면
   답을 정한 뒤 **`FAQ.md`에 추가한다** — 그 질문은 반드시 다시 나온다.
5. 공개 경로에서 못 보는 조건부 질문과 사람 결정값은 `submission.md`에 정확한 요청으로 남긴다.
6. 위 §`ready` 계약을 확인한다. **제출은 GLG가 승인한다.** 아래 §경계.
7. GLG가 제출 완료를 알리면 즉시 **두 곳을 함께 닫는다**.
   - `LEDGER.md`: `submitted` + 지원일
   - 해당 `submission.md`: `submitted` + 실제 업로드 사본 + 완료 기록
   개인 필드 값은 적지 않고 “GLG가 브라우저에서 완료, 값 미보존”으로 남긴다.
8. `./check.py`가 통과하기 전에는 제출 판을 끝났다고 보고하거나 커밋하지 않는다.
