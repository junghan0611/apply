# AGENTS.md — applications/ (지원 실행 · 제출 기록 레인)

이 디렉터리는 문서를 **만드는** 곳이 아니라 **내는** 곳이다. 만드는 곳은 둘이다.

| 레인 | 위치 | 성격 |
|---|---|---|
| **dossier 발사대** | `../dossier/` | 한 건에 조준한 두꺼운 3종 세트 — **깊이 축** |
| 이력서 발사대 | `../resume/` | 공통 프레임 → 타깃별 컷 6종 |
| **지원 실행·기록** | **`.` (여기)** | **어디에 · 언제 · 무엇을 냈는가** — **넓이 축** |

> **지금은 넓이 축이다** (2026-07-29 GLG). 이 레인의 방향은 **여러 곳의 제출 플랫폼을 갖추는
> 것**이고, 다 갖춰지면 `../dossier/` 의 깊이 축으로 넘어간다. 낼 곳이 갖춰지기 전에 문서
> 깊이를 파지 않는다.

여기의 목적은 하나다. **"어디 냈는지 모르는 상태"를 만들지 않는다.** 하루에 열 곳을 내면
2주 뒤 연락이 왔을 때 어느 공고인지 모른다. 공고는 마감되면 사라진다. 그래서 낼 때 남긴다.

## 원장(LEDGER)이 SSOT다

`LEDGER.md` 한 장이 전체 지원 이력이다. 건마다 폴더가 하나 생기고, 원장에 행이 하나 는다.

```
applications/
  LEDGER.md               ← 전체 지원 이력 (SSOT)
  FAQ.md                  ← 폼·면접 답변 사전 — 값 + 근거 + 화법 (폼 채울 때 여기서 가져온다)
  INBOX.md                ← 후보 대기열 + 지원 경로(플랫폼별) 확인 결과
  new.sh                  ← 건 생성 + 원장 행 추가
  <company>--<role>/
    JD.md                 ← 공고 출처·필요 인용·요약 (전문 복제 금지)
    submission.md         ← 무엇을·언제·어떻게 냈는지 + 공개 가능한 질문과 답
    submit/               ← 업로드 파일명·source·지문 (실제 바이너리는 private 보관면)
    (필요시) cover-letter.md · pre-question.md · referral-summary.md · build.sh
  _archive/               ← 마감·불합격 건 (원장 행은 남긴다)
```

**선택 슬롯은 이름이 정해져 있다.** 같은 것을 매번 다른 파일명으로 만들지 않는다.

| 파일 | 언제 | 무엇이 들어가는가 |
|---|---|---|
| `cover-letter.md` | 폼에 자유서술 칸이나 커버레터 첨부가 있을 때 | **붙여넣을 본문**과 왜 그렇게 썼는지 |
| `pre-question.md` | 사전질문 서술형이 여러 개일 때 | 문항별 답과 글자수 |
| **`referral-summary.md`** | **추천으로 들어갈 때** | 역할 수준의 경로와 **추천서 주장 ↔ 서류 증거 대조표**. 추천인 신원·원문 없음 |
| `build.sh` | 첨부를 조립해야 할 때 | 제출 직전 한 번 돌려 최신 컷을 `submit/` 로 복사 |

추천이 붙어도 **추천서를 서류 본문에 인용하지 않는다.** 추천은 추천인의 문장이고 서류는 내
문장이다. public repo에는 추천인 실명·소속·관계·원문을 두지 않고, 공개 동의를 새로 받은 경우가
아니면 `referral-summary.md`에 주장과 증거의 구조만 남긴다. 원문은 private 보관면이 소유한다.

### 검수는 소스가 아니라 제출 세트 위에서 한다 (2026-07-29 GLG)

**GLG 는 org/md 를 읽지 않는다. 그 업체에 올라갈 파일 세트를 그대로 연다.**

```bash

```

`stage.py` 가 각 건 `submit/` 에 **나갈 물건 전부**를 깐다 — `submission.md` §첨부 컷에서

`cover-letter.md` §붙여넣을 본문을 뽑은 `cover-letter.txt`(폼이 textarea 다),
그리고 `README.md`(어느 파일이 폼의 어느 칸인지) + `MANIFEST.sha256`.

### ⭐ 이력서 한 장으로 끝내지 않는다 (2026-07-30 GLG)

> **GLG**: *"이력서만 낼 게 아니라 가능하면 포트폴리오랑 경력기술서 내면 좋거든. 오전에 하나
> 내는데 딸랑 이력서 하나 준비되어있더라. 그냥 하나만 내기에는 성의가 없다."*

**두 행이 첨부를 정한다.** 표에 이렇게 쓴다 — `stage.py` 가 경로를 정규식으로 읽는다.

| 행 | 무엇 | 어디서 |
|---|---|---|
| `첨부 컷` | 폼의 **필수** 이력서 슬롯 | `resume/build/*.pdf` |
| `추가 첨부` | 폼의 **선택** 슬롯(경력기술서·포트폴리오) | `dossier/build/*.pdf` |

- **`추가 첨부` 행이 없으면 깊이 문서를 깔지 않는다.** 낼 수 없는 파일을 세트에 두지 않는다.
- **슬롯 미실측은 「없음」이 아니다.** 2026-07-29 판 기록들이 「추가 서류 — 없음」이라고
  적어 두었는데 그것은 *낼 물건이 없다*는 뜻이었고 **폼에 칸이 없다는 확인이 아니었다.**
  못 읽은 폼은 **「미실측 — 있으면 올린다」**로 적고 파일은 깔아 둔다. 카페·이동 중에 폼을
  열었을 때 파일이 그 폴더에 없으면 그 자리에서 못 낸다.
- **선택 첨부를 올리면 동의 항목이 하나 더 붙는 폼이 있다.** Lunit 「(선택) 추가 지원 서류
  수집 동의」·한화비전 「선택항목 수집 동의」. **미동의로 내면 올린 파일이 처리되지 않는다.**
- **첨부를 늘리는 것이 성의가 아니다.** 그 자리에 맞는 것을 내는 것이 성의다 — **Embedded 컷
  건에는 AX 축 깊이 문서를 붙이지 않는다**(Bear·Telechips·Telit·Sonatus). 근거는 각 건
  `submission.md` §낸 것 아래 인용 블록.
- **깊이 문서는 회사 중립판이 정본이다.** 특정 회사를 조준해 빌드했으면 **다른 건에 그대로
  깔지 않는다.** 조준문은 `competency.org` 프롤로그에 있고, 나간 뒤에는 중립으로 되돌린다.
  검사: `gs -q -sDEVICE=txtwrite -o - <pdf> | grep -ciE '<회사명>'` (서버엔 `pdftotext` 가
  없고 **빈 결과를 「깨끗함」으로 오독**한다).
### 🔴 PDF 는 git 에 넣지 않는다 — org 가 정본이고 지문이 증언한다 (2026-07-30 GLG)

> *"git 에 넣지말고 org 있으니까 제출할때 생성하게 하자. 그리고 org 를 각 위치에 저장하면돼.
> 그걸로 재현되니까. pdf는 넣을수록 리포가 지저분해지니까"*

`.gitignore` 가 `applications/*/submit/*.pdf` 를 전부 막는다. Portfolio 하나가 **3.8MB** 이고
11건이면 43MB, 재빌드마다 새 blob 이 쌓인다.

**그럼 「그때 무엇을 냈는가」는 무엇이 증언하나 — git 에 남는 두 파일이다.**

| 파일 | 무엇을 증언하나 |
|---|---|
| `submit/MANIFEST.sha256` | **그때 낸 파일의 identity commitment.** 파일이 있으면 **바이트 동일 여부를 판정**하고, 없으면 증언만 보존한다 |
| `submit/SOURCES.md` | **어느 org·어느 명령으로 재현하는지** + 세트를 깔 때의 커밋 SHA |

⚠ **지문과 재현을 혼동하지 않는다** (2026-07-30 GPT 교차검수 J5). `MANIFEST` 는 **과거
identity 의 약속**이고 `SOURCES` 는 **재생성 경로**다. 원본 바이트를 버린 뒤 비결정적 빌드가
지문과 어긋나면 「달라졌다」는 알지만 **무엇이 달라졌는지는 말하지 못한다.**
그래서 「재현본이 같은지 검증된다」로 쓰지 않는다 — **「바이트 동일 여부를 판정한다」**가 사실이다.

🔴 **「PDF 가 git 에 없다」는 절대명제가 아니다.** gitignore 는 이미 추적 중인 파일에 무효라서
실제로는 이렇다 — **막히는 것은 새로 늘어나는 깊이 PDF** 이고, **이력서 컷 27건과 제출 완료
건의 스냅샷은 tracked 로 남아 `git pull` 로 온다.** 문서에 이 구분을 흐리게 쓰면
**노트북에서 「낼 파일이 없다」로 오독해 제출을 포기**하게 된다.

- 옛 `nhn/build/` 결함(§`submit/`)과 다르다. **그때는 지문도 재현 경로도 없었다.**
- **`submitted` 로 닫을 때 `MANIFEST.sha256` 이 비어 있으면 `check.py` 가 FAIL 한다.**
  스냅샷 PDF 대신 지문이 그 자리를 지킨다.
- 이미 tracked 인 PDF(AIRS·NHN·한화·AutoEver·DEEPX·Enhans·Holiday)는 그대로 둔다 —
  **히스토리를 다시 쓰지 않는다.**

🔴 **그래서 다른 기계에서는 빌드가 선행된다.** clone·pull 만 하면 `submit/` 에 PDF 가 없다.
제출 세션 맨 앞에서 이 순서를 돌린다 — `SUBMIT-QUEUE.md` §0 이 정본이다.

```bash
(cd resume   && ./run.sh all)
(cd dossier  && ./run.sh competency && ./run.sh portfolio)
applications/stage.py
applications/check.py --deep      # ⭐ 조준 누출을 여기서 잡는다
```

### `./check.py --deep` — 조준 누출은 기계가 잡는다

`dossier/` 정본은 **한 벌**이고 `competency.org` 프롤로그 한 줄이 조준 자리다. 한 건을 조준해
빌드한 뒤 중립으로 되돌리지 않으면 **다음 건 세트에 앞 회사 이름이 실려 나간다.**
2026-07-30 아침에 실제로 AIRS 조준판이 남아 있었고, 그 상태로 `stage.py` 를 돌리면
Lunit·SOCAR 에 *"AIRS Medical AX 팀이 만드는…"* 이 붙는다. **눈으로는 못 보는 사고다.**

- `--deep` 은 `gs` 로 깊이 문서 본문을 읽어 **다른 건의 회사 이름**을 찾는다. 26개 · 약 20초.
- **앞 6,000자만 본다.** 첫 판은 본문 전체를 봤고 참고문헌의 `OpenAI, "Codex cli." 2025`
  (문서 93% 위치)를 조준으로 읽어 **12건을 오판**했다. 회사 이름은 기술 스택·인용으로
  정당하게 등장한다 — **조준은 앞머리에만 있다.**
- `gs` 로 본문을 못 읽으면 **판정하지 않고 그 사실을 보고한다.** `pdftotext` 는 이 서버에
  없고, 없는 채로 부르면 **빈 결과가 「깨끗함」으로 읽힌다.**

- **수정 요청이 오면 `submit/` 을 손으로 고치지 않는다.** `resume/body.org` · `targets/*.org` ·
  `dossier/*.org` · `cover-letter.md` 를 고치고 **빌드 → `./stage.py`** 로 세트를 다시 깐다.
  세트 단위로 움직여야 제출본과 소스가 갈라지지 않는다.
- **`submitted` 인 건은 `stage.py` 가 건드리지 않는다.** 그때 나간 파일이 사실이다.
- 이력서·dossier 를 재빌드했으면 **`./stage.py` 를 반드시 뒤따라 돌린다.** 안 그러면
  세트가 옛 판이다.

### `submit/` — 건마다 사본을 둔다

**제출지마다 내라는 것이 다르다.** 어디는 영문 이력서 한 장, 어디는 국문 자기소개서, 어디는
사전질문 서술형, 어디는 경력기술서를 따로 받는다. `resume/build/` 는 **베이스 발사대**이고,
건마다 무엇을 올렸는지는 **그 폴더의 `submit/` 이 증언한다.**

- `resume/build/` 를 가리키는 링크로 두지 않는다. **사본을 둔다.** 발사대는 계속 갱신되므로
  링크만 두면 3개월 뒤 「그때 무엇을 냈는지」가 사라진다.
- 그 건에만 필요한 문서(국문 자기소개서, 사전질문 답변)는 **그 폴더에서 만든다.**
  `resume/` 를 오염시키지 않는다.
- 폴더에 `build.sh` 를 두어 **제출 직전에 한 번 돌려 최신 컷을 다시 복사**하게 한다.
  발사대가 그 사이에 갱신됐을 수 있다.
- `submit/` 은 git 으로 추적한다. 이력서 컷만 내는 건은 100~200KB 수준이고, dossier 를 내는
  건은 몇 MB 가 된다. **무엇을 냈는지가 이 저장소의 존재 이유다.**
- **발사대의 `build/` 가 gitignore 라는 이유로 `submit/` 을 비워 두지 않는다.** NHN AX 건이
  2026-07-29 까지 그 상태였다 — 낸 파일이 git 에 없었다. 발사대는 무시해도 되지만
  **사본은 반드시 커밋한다.**
- **10MB 넘는 첨부(증거 패키지 ZIP 등)는 해시로 대신할 수 있다.** 단 조건이 둘이다:
  ① 그 내용물이 이 저장소에 이미 추적되고 있을 것, ② `submit/MANIFEST.sha256` 에 해시를
  남길 것. 조건을 못 채우면 용량이 커도 파일을 넣는다.

**폴더 이름은 `<company>--<role>`이고 전부 영문 소문자 하이픈이다.** 한글 폴더명을 만들지
않는다 — 외부 ATS 업로드·zip·CI 어디서든 깨지지 않아야 하고, 경로를 눈으로 훑을 때 영문 한
벌이 읽기 쉽다. 한글 표기는 `JD.md` 안에 남는다. `new.sh`는 한글만 들어오면 슬러그가 비어
**멈추고 영문을 요구한다.**

날짜는 폴더명에 넣지 않는다 — 같은 회사에 다시 낼 때 헷갈린다. 날짜는 원장과
`submission.md`에 있다.

### `JD.md` — 요약이 아니라 출처가 있는 원문

공고는 다음 순서로 원본을 찾는다.

1. 회사 공식 채용 보드와 원본 ATS;
2. LinkedIn 정식 공고;
3. LinkedIn 개인 채용 포스트;
4. Wanted·Remember·사람인·잡코리아 등 폐쇄 채널의 흔적;
5. 검색 캐시·회사 팀 글.

뒤쪽 출처에서 제목이나 흔적만 찾았으면 그것을 전문처럼 늘리지 않는다. `JD.md` 상단에는 최소한
**확인한 URL · 확인일 · 원본 ATS 여부 · 현재 열림 여부 · 본문 전문/일부/미확인**을 보이게 둔다.
LinkedIn에서 원본 ATS로 옮겨 갔다면 두 URL의 동일 공고 근거도 남긴다.

`JD.md` 본문은 면접 때 다시 인용할 수 있는 원문이어야 한다. 요약·적합도·추천 이유·경계는
`submission.md`가 쥔다. 원문을 못 얻었다면 `본문 미확인`이 값이고, 닫힌 플랫폼의 검색 흔적만으로
요건을 완성하거나 `ready`로 올리지 않는다.

### `ready`의 뜻

`ready`는 “PDF 하나가 있다”가 아니라 **노트북에서 새 문서 작업 없이 검토·개인값 입력·업로드·
Submit만 하면 되는 상태**다. 다음이 한 건의 `submission.md`에 보여야 한다.

- 현재 열려 있는 정확한 공고와 지원 URL;
- 보존한 JD 원문과 출처 수준;
- 필수요건·고용형태·근무지·언어·비자에서 확인한 것과 미확인인 것;
- 왜 이 회사의 이 직무를 골랐는지와 정면 증거·하드 갭;

#### `breezy.hr` — Bear Robotics (2026-08-09 실측)

`<company>.breezy.hr/p/<id>-<slug>/apply`. **한 화면 폼**(위저드 아님) · 가입 불필요 ·
AngularJS 라 **폼 스키마가 HTML 안에 통째로 들어 있다.** 브라우저를 열기 전에 `curl` 로 읽는다.

```bash
curl -sA "$UA" "<지원URL>" |
  grep -o '<input type="hidden" id="questions" value="[^"]*"'   # 질문지 JSON 전문
# 필수/선택은 별도 hidden 이 말한다: resume_required · work_required · education_required
#                                   · summary_required · cover_letter · eeoc
```

- ✅ **네이티브 file input 이 DOM 에 있다**(`name="cResume"`). ninehire 와 다르다 —
  **에이전트 업로드가 가능할 것으로 보인다**(실제 업로드는 아직 미검증).
- **서술 칸이 둘이다** — `cSummary`(Experience Summary) · `cCoverLetter`(Cover Letter).
  회사마다 required/optional 이 다르고 **hidden 값이 사실이다.**
- **질문지는 분기한다.** 「장애·보훈 → 네」가 증빙파일 **필수** 칸을 열고, 「국적 → Non-Korean」이
  Visa sponsorship 칸을 연다. **분기 뒤 칸까지 읽어야 폼을 안 것이다.**
- ⚠ **EEOC(인종·성별) 라디오가 `required` 로 렌더될 수 있다** — 미국 본사 계열. 응답 거부
  선택지가 있고 **사람이 고른다.**
- 🔴 **honeypot 필드(`hp_*`)와 `form_token` 이 있다.** 봇 방지 축이 걸려 있으므로
  **폼 채우기는 브라우저에서 사람이 한다.**
- **화면은 2단계다.** `curl` 로 읽은 HTML 에는 질문지·EEOC 가 한 장에 다 있지만, UI 는
  **「계속」** 버튼으로 나눠 보여 준다. **「HTML 에 다 있다」를 「한 화면이다」로 읽지 않는다.**
- **EEOC 는 `ng-required` 로 렌더되지만 화면 문구는 `requested (not required)`** 이고 응답
  거부 선택지가 있다. **DOM 의 required 를 사람에게 「필수」라고 전하지 않는다.**
- 실측 원문: `bear-robotics--systems-software-engineer-linux-platform/submission.md` §폼 실측.

   제거했다(`docs/HISTORY-REDACTION.md` §dense-pii-form). 원본은 private Org 면이 소유한다 —
   여기서 파일을 찾지 말고 GLG 에게 그 한 벌을 열어 달라고 요청한다.
3. **고치기 전에 GLG 승인을 받는다.** 재직 신고는 사람의 값이다. 「명백히 틀렸으니 고친다」로
   혼자 가지 않는다 — 무엇이 틀렸는지 보이고, 지울지 다시 넣을지를 GLG 가 고른다.
4. **재직 중인 회사는 종료일을 비운다.** 파서는 오늘 날짜를 퇴사일로 넣는다.
5. 값을 **케이스 파일로 복사하지 않는다.** 어느 칸에 무엇이 들어갔는지만 적는다
   (§제출 스냅샷은 다음 건의 입력값이다).

#### `recruiter.co.kr` — 카카오뱅크 인재풀 (2026-07-30 실측)

`kakaobank.recruiter.co.kr/v1/applicant/resume-form/<id>?step=N`. 3단계 위저드
(기본정보 → 학력 및 연구/경력 → 최종 점검) · 세션 2시간 + `연장` · 단계 이동마다 자동 저장.

- ✅ **`file_upload` 가 동작한다.** ninehire(Enhans·한화비전)에서 막혔던 것과 다르다 —
  저장소 경로를 그대로 올렸다(PDF 3종). **recruiter.co.kr 은 에이전트 업로드 가능.**
- **경력기술서 슬롯은 행 무제한**이고 각 행이 **파일 또는 URL** 중 하나다. 이력서 전용 칸이
  없어 구조화 폼 자체가 이력서 역할을 한다 — 영문 CV 는 이 슬롯에 넣는다.
- **학력 재학기간은 `YYYY.MM`**(데이트피커가 연 → 월, 일 없음). 학교명·전공명은 **사전 검색형**
  이라 임의 문자열이 안 들어간다. 졸업구분에 **`수료`** 가 있어 박사 수료가 정확히 표현된다.
- 🔴 **필수 공백이 있어도 단계 이동·임시저장이 통과한다.** 검증은 `최종 제출`에서 걸린다 —
  **「다음이 눌렸으니 다 채워졌다」로 읽지 않는다.**
- ⚠ **최종 점검 화면이 좁은 뷰포트에서 렌더되지 않는다** — *"모바일 환경에서는 확인할 수 없어요"*.
  에이전트 뷰포트(924px)가 모바일 판정이다. **미리보기 검토는 사람 화면 또는 PDF 다운로드로.**
- 🔴 **직무 목록에 AI·ML·Agent 가 없다**(57개 중). 판단 기록은
  `kakao-bank--talent-pool-platform-development/submission.md` §지원분야를 왜 이것으로 골랐나.

🔴 **공고 목록은 이 ATS 에 없다 — 회사 채용홈이 따로 개편됐다 (2026-07-30 실측).**
`kakaobank.recruiter.co.kr/appsite/company/index` 는 *"인재영입 홈페이지가 개편되었습니다
→ https://recruit.kakaobank.com/"* 안내만 띄운다. **목록은 새 홈(Next.js)에 있고 지원 폼만
recruiter.co.kr 이다.**

- 새 홈은 클라이언트 렌더라 `boards.py` 로 안 훑힌다. **경로는
  `window.__BUILD_MANIFEST.sortedPages` → `/jobs`** 이고, 목록 페이지에서
  `a[href*="/jobs/"]` 로 25건 전부(제목·직군·마감·공고 ID)를 뽑았다.
- ⚠ **`javascript_tool` 이 이 두 도메인에서 자주 `[BLOCKED: Cookie/query string data]` 로
  끊긴다.** 결과에 URL 쿼리스트링이 섞이면 차단되므로 `href.split('?')[0]` 처럼 **잘라서
  반환**한다. 안 되면 `read_page`·스크린샷으로 넘어간다.
- 「지원서 작성」 링크는 `target=_blank` 인데 **MCP 탭 그룹 밖으로 열려 보이지 않는다.**
  `a.target='_self'` 로 바꿔 클릭하면 같은 탭에서 폼으로 들어간다.

🔴 **공고 지원 폼은 인재풀 폼과 다르다 — 「인재풀을 냈으니 폼을 안다」로 읽지 않는다.**
공고 폼에는 **인적사항(현주소) · `직장경력 *` · 포트폴리오 란 · 자격증 란 ·
자기소개서 2문항(각 1,000자, 필수)** 이 붙는다. 원문은
`kakao-bank--data-engineer-data-warehouse/JD.md` §지원 폼 스키마.

- **로그인 전에 동의 화면이 먼저 나온다** — 개인정보·민감정보 **둘 다 필수**이고 거부하면
  지원이 불가하다. 화면에 **reCAPTCHA** 가 붙어 있다.
- 민감정보 동의의 목적은 **「장애인 고용촉진 및 직업재활법에 따른 장애인 우대」 하나**다.
- ✅ **희망 연봉·현재 연봉·입사 가능일을 묻지 않는다.**

## 경계 — 에이전트가 넘지 않는 선

- **제출(Submit·지원하기·최종 확인) 버튼은 GLG의 명시 승인 없이 누르지 않는다.** 세션마다,
  건마다 따로 받는다. 한 건의 승인이 다음 건으로 이어지지 않는다.
- **계정 설정·프로필을 임의로 바꾸지 않는다.** 저장된 이력서 교체처럼 워크플로에 필요한
  변경은 GLG에게 알린 뒤 한다.
- **답을 지어내지 않는다.** 연차·비자·희망연봉·입사가능일은 `FAQ.md`에 GLG가 확정한
  값만 쓴다. 사전에 없으면 **묻는다.** 폼을 비워 두는 편이 틀린 값을 넣는 것보다 낫다.
  민감한 법적 값은 브라우저에서만 확정하고 Git에는 처리 규칙만 남겨도 된다.
- **개인정보를 원장에 적지 않는다.** 주민번호·계좌·비밀번호는 어떤 폼에도 에이전트가
  넣지 않는다 — GLG가 직접 입력한다.
- 회사명·공개 지원 경로·결과는 남긴다. 개인화 candidate URL, 회신 UUID, 추천 경로·신원,
  로그인 뒤 자동화 정보는 남기지 않는다. raw 원본과 public 기록을 자동 동기화하지 않는다.
- **감독형(프록터링) 온라인 시험 — 웹캠·화면공유·폰 촬영이 붙는 코딩테스트·인적성검사는
  응시 시작 후 에이전트가 문제를 풀거나 답을 대신 입력하지 않는다.** 준비 단계(연습 문제·
  환경 세팅·과거 후기 조사)까지만 같이 한다. 감독관 없는 자율 서술형(자기소개서·사전질문)
  과는 다른 경계다 — 시험 감독이 붙는 순간 그 결과는 GLG 혼자의 것이어야 한다.
