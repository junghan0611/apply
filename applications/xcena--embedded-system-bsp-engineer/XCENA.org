- [보도자료/조사 인계] [[https://www.prnewswire.com/news-releases/semifive-collaborates-with-metisx-in-developing-cxl-based-memory-accelerator-chip-302125756.html][SEMIFIVE 협업 발표, 2024-04-24]]에서 *프로토타입 설계 및 Samsung 4nm 양산 개발 협업*을

*가설 갱신*: 범용 IP·설계 파트너를 활용한다는 얼개는 공개 협업과 양립한다.
그러나 「완성된 외부 개발 보드를 받아 솔루션을 얹는다」는 주장은 근거가 없다.
현재 공개 설명에 더 가까운 모델은 *자체 핵심 아키텍처를 외부 설계 플랫폼·IP·제조와 결합한 SoC 제품화*다.
초기 검증 플랫폼의 구성은 여전히 미확인이다.

** 가설과 사실을 가르는 기준

[가설, GLG가 2026-10-13 제시] 소규모 팹리스는 범용 구성·벤더 IP·개발 환경을 활용하고,
핵심 프로세서·캐시·스토리지 솔루션의 제품화에 집중할 가능성이 있다.
「개발 보드를 받아 기능을 얹는다」는 공급 구조는 아직 확인하지 않았다.

- CXL 표준 준수 ≠ CXL 컨트롤러·PHY를 자체 설계했다는 증거.
- ARM 코어 채택 ≠ ARM ISA나 코어를 직접 설계했다는 뜻.
- RISC-V ISA 채택 ≠ 코어 마이크로아키텍처의 구현 주체가 밝혀졌다는 뜻.
- 파운드리 제조 ≠ 파운드리에서 완성 칩 설계를 받아왔다는 뜻.
- 보드 공급·라이선스 IP·외주 설계·자체 RTL·파운드리 제조는 별개의 계약이다.
- 팀 규모만으로 기술 소유 범위를 추정하지 않는다. 현재 정확한 인원은 본 문서에서 확정하지 않는다.

** 제품의 문제를 한 문장으로 읽기

[가설] AI·데이터 처리에서 메모리 용량과 데이터 이동 비용이 병목일 때,
호스트의 메모리 공간을 확장하고 데이터 가까이에서 처리하는 반도체·소프트웨어 스택.
「AI 에이전트 제품을 만드는 회사」와 「AI 워크로드에 필요한 시스템을 만드는 회사」는 다르다.
후자의 어떤 워크로드를 어느 계층에서 개선하는지 확인한다.

** 공식 제품 자료에서 읽힌 구성

[공식/조사 인계] [[https://xcena.com/computational_memory][Computational Memory 제품 페이지]]의 PoC 브리프:

- CXL Type 3 메모리 장치와 메모리 확장·근접 연산을 제시한다.
- 관리 프로세서: *듀얼 Arm Cortex-A53*.
- 데이터 가속 프로세서: 다수 RISC-V 코어.
- 호스트 연결: PCIe/CXL. SSD 연결 경로에 PCIe Root Complex 및 SSD RAID 지원을 제시한다.
- DDR5와 SSD를 결합하는 InfiniteMemory를 제시한다.

*제품표의 주의사항*: 「강조된 기능은 양산 시 지원」이라는 각주가 있다.
크롤 텍스트에서 강조 표시가 소실되어 어떤 기능이 현재 PoC에 있는지 분리하지 못했다.
제품 페이지의 표를 현재 실리콘에서 모두 동작하는 기능 목록으로 읽지 않는다.
코어 수·클럭은 공식 PoC와 발표 해설이 다르므로 한 수치로 합치지 않는다.

** 발표 해설에서 읽힌 동작

[보도/조사 인계] [[https://chipsandcheese.com/p/hot-chips-2026-xcena-and-samsungs][Chips and Cheese의 Hot Chips 2026 해설]]:
SSD-as-memory 경로에서 DRAM을 페이지 캐시로 사용하고, 캐시 미스를 RISC-V 코어의 펌웨어가
처리한다는 설명이 있다. *공식 제품 페이지에서 이 펌웨어 책임 경계를 확인한 것은 아니다*.
메모리 접근의 투명성·캐시 미스 비용·주소 변환·오류 복구가 서로 어떻게 연결되는지 읽을 단서다.

[공식/조사 인계] Hot Chips 발표 원본 슬라이드는 등록자 대상이며 공개 예정은 12월 초라는 FAQ를
형제가 확인했다. 전체 공식 발표 덱을 읽었다고 하지 않는다.
[[https://www.servethehome.com/xcena-mx1-cxl-computational-memory-device-at-hot-chips-2026/][ServeTheHome 현장 보도]]는 별도 2차 자료다.

[슬라이드 이미지/조사 인계, 09:15 갱신] Sonnet이 STH 게시 슬라이드 이미지
3·4·6·7·8·9번을 열람했다. 회사 발표를 매체가 재게시한 것으로, 주장과 구현 검증은 다르다.

- 슬라이드 3: 내부 NoC·DRAM Controller·L3 Cache·연산 클러스터 구성.
- 슬라이드 7: 호스트와 연산 코어의 가상주소 공간 연결, CXL-aware allocator,
  테넌트별 페이지 테이블, BI-Snoop.
- 슬라이드 8: PXL Runtime Lib → Device Lib → Kernel Driver + Resource Manager → 장치.

[가설] 캐시·주소 변환·할당 정책과 장치 실행 경로를 같이 다루는 구조가 보인다.
캐시 미스 처리의 실제 HW/FW 분담은 이 이미지 열람만으로 닫히지 않는다.
발표·제품 라인업·PoC의 코어 수가 서로 달라 모델/세대 차이를 확인하기 전 단일 수치를 쓰지 않는다.

** AI 데이터센터에 들어가면 무엇을 하는가

[공식 자료·조사 인계를 연결한 제품 해석] MX1은 CPU의 로컬 DRAM 전체를 대신하는
장치라기보다 *CXL로 추가하는 메모리 계층과 선택적 근접 연산 장치*로 읽힌다.
실제 사용할 기능은 Expand/Compute 등 모델·구성·지원 SW에 따라 구분해야 한다.

- *호스트에서 보이는 역할*: 추가 메모리 용량. DRAM 기반 확장과 SSD-backed 확장은
  구성을 나누어 읽는다. 장치 접근이 load/store라는 점은 지연이 로컬 DRAM과 같다는 뜻이 아니다.
- *장치 내부의 역할*: InfiniteMemory 설명에서 DRAM은 SSD-backed 데이터의 페이지 캐시다.
  장치 전체가 CPU의 L3/LLC 캐시라는 뜻은 아니다.
- *근접 연산의 역할*: 지원하는 처리 일부를 데이터 가까이에서 실행해 호스트로 옮길 데이터를 줄인다.
- *애플리케이션의 역할*: 이 용량에 KV 캐시 등을 둘 수 있다. KV 캐시는 애플리케이션 데이터 구조다.
  장치 내부 DRAM 페이지 캐시·CPU 캐시와 구분한다.

#+begin_example
서버 CPU ─ 로컬 DRAM  : 가까운 작업 메모리
    │
    └─ CXL 장치       : 추가 메모리 계층
          ├─ DDR DRAM : 확장 메모리 / 구성에 따라 SSD 페이지 캐시
          ├─ NVMe SSD : InfiniteMemory의 용량 계층
          └─ 연산 코어: 지원 작업의 근접 처리
#+end_example

[가설] 배치는 「뜨겁고 지연에 민감한 것은 가까운 DRAM, 크고 덜 민감한 것은 확장 계층」을
생각하는 출발점이다. 실제 정책은 OS·런타임·장치가 나눠 맡을 수 있으며 자동 최적화를 가정하지 않는다.
용량 확장과 빠른 접근은 서로 다른 목표다. 캐시 미스·데이터 이동·접근 패턴에 따라 효과가 달라진다.

* Optane PMem에서 엑시나로 — 문제의 연속성과 차이

메모리 인덱스, NUMA 배치 문제를 모두 다뤘다고 밝혔다. 위 세 축을 경험 미확인으로
되묻지 않는다. 논문별 구현·실험 조건은 필요할 때 원문으로 좁힌다.

** FTL 비유 — 구현이 아니라 책임을 비교

[분석] SSD는 코어·메모리·플래시를 포함한 시스템이고, FTL은 논리 블록 주소와 물리 플래시
사이에서 매핑·배치·회수·wear leveling 등의 책임을 진다.
엑시나의 캐시·주소 변환·티어링도 서로 다른 매체를 상위 SW가 사용하는 방식과 비용을
중재한다는 점에서 비슷한 질문을 던진다. *FTL과 엑시나 구현이 같다는 주장은 아니다*.

- FTL의 경계: 호스트의 블록 I/O ↔ 플래시 페이지/블록의 물리 제약.
- 엑시나의 공개 제품이 제시하는 경계: 호스트 메모리 접근·근접 연산 ↔ 장치의 DDR/SSD 계층.
- InfiniteMemory가 SSD를 메모리로 노출할 때도 SSD 안의 FTL을 대체한다는 근거는 없다.
- 독자성은 SW 정책만이 아니라 캐시·MMU/TLB·NoC·컨트롤러 등의 HW와 실행 SW를
  함께 구성하는 아키텍처일 수 있다. 구체 HW/FW 분담은 미확인이다.

** PMem과 CXL — 같은 기술이 아니라 같은 질문이 이어진다

| 질문 | Optane PMem 연구에서의 좌표 | 엑시나 제품에서의 접점 |
|------+----------------------------+------------------------|
| 서로 다른 메모리 비용을 어떻게 드러내는가 | DRAM과 PMem의 지연·대역폭·읽기/쓰기 차이 | DDR/SSD 계층·캐시·메모리 확장 |
| 데이터를 어디에 두는가 | NUMA 지역성·배치·노드 복제 | 호스트/장치 배치·티어링·주소 변환 |
| 어떤 추상화를 SW에 제공하는가 | 자료구조·파일/블록 인터페이스·PM 접근 방식 | CXL 메모리 노출·공유 VA·allocator |
| 데이터 이동을 어디에서 줄이는가 | 메모리 계층을 고려한 자료구조·알고리즘 | 데이터 가까이에서 처리하는 연산 구조 |
| 무엇이 영속성을 보장하는가 | 모드·flush/fence·장애 시 보장 확인 필요 | CXL 자체나 SSD 존재만으로 보장되지 않음 |

위 표는 개념적 연결이다. GLG가 모든 행의 구현을 수행했다는 뜻이 아니다.
*CXL은 연결·메모리 접근/일관성 등의 프로토콜이며 PMem은 매체·접근·영속성의 문제다*.
CXL 장치가 반드시 비휘발성인 것은 아니다. SSD를 쓰는 메모리 장치도 휘발성 캐시와
복구·쓰기 완료 규칙에 따라 영속성 의미가 달라질 수 있다.
캐시 일관성(coherence) ≠ 장애 후 일관성(crash consistency).
Optane의 실제 사용 모드가 Memory Mode/App Direct 중 무엇인지 확인 전 영속성 경험을 확대하지 않는다.

** 09:36 조사 — 회사가 직접 설명한 연결

[공식 블로그/조사 인계, Sonnet 09:36]
[[https://medium.com/xcena-blog/how-we-solved-the-kv-cache-bottleneck-in-llm-inference-with-cxl-shared-memory-d5133dcfb044][XCENA BLOG 2026-05-21]]은 CXL.mem을 장치 연결 메모리에 load/store로 접근하는
인터페이스로 설명하며, 내장 연산과 storage tiering을 결합한 메모리 계층을 강조한다.
이 설명을 로컬 DRAM과 지연·장애·영속성 의미가 모두 같다는 주장으로 읽지 않는다.

[공식 블로그/조사 인계]
[[https://medium.com/xcena-blog/cxl-usecase-how-far-have-we-come-and-whats-next-1f96c407cfb3][XCENA BLOG 2025-09-05]]은 SSD의 지연·대역폭이 DRAM과 달라 무작위 접근에는
불리할 수 있고, 예측 가능한 접근에는 read-ahead·DRAM 버퍼·prefetch가 도움이 된다고 설명한다.
같은 글의 AutoNUMA·TPP·interleaving은 호스트 배치 기법 설명이다.
호스트 정책을 모두 장치 내부 정책으로 바꾸어 적지 않는다.

[회사 슬라이드/조사 인계]
[[https://www.servethehome.com/wp-content/uploads/2026/08/hot-chips-2026-xcena-mx1-cxl-slide-07.jpg][Hot Chips 슬라이드 7 게시 이미지]]는 호스트와 MU의 단일 가상주소 공간,
CXL-aware allocator, 호스트 VA→PA 페이지 테이블, 테넌트별 격리를 제시한다.
따라서 연구 접점은 단순한 용량 확장뿐 아니라 *주소·배치·지역성·공유 데이터의 관측*에 있다.

[미확인] 이번에 읽은 제품 자료·블로그·슬라이드 범위에서 영속성·장애 후 데이터 보존
보장을 찾지 못했다. 부재 증명은 아니며 InfiniteMemory의 dirty page 쓰기 완료·write-back·
전원 차단 의미는 확인할 항목이다. Optane App Direct와 동일한 의미를 가정하지 않는다.

[가설, 연구를 연결해 물을 질문] SSD 위의 DRAM 페이지 캐시에서 dirty 데이터 추적·
write-back 단위가 접근 입도와 다르면 쓰기 증폭이 쟁점일 수 있다.
엑시나에서 실제 병목이라는 근거는 없다. NVM 쓰기 증폭 연구를 옮겨 질문할 수 있는 자리다.
