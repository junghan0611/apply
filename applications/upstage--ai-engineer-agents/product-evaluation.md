# Upstage 제품 체험 평가 — 제출 원고

> 폼의 문항 1에 아래 `붙여넣을 본문`만 넣는다. 이 파일의 검증 좌표는 제출문이 아니라
> 주장·날짜·산출물의 계보를 보존하는 작업 기록이다.

## 붙여넣을 본문

제품을 점수로 줄 세우는 글은 쓰지 않겠습니다. 제가 확인하고 싶은 것은 더 단순하고도 오래 걸리는 질문입니다. 이 모델과 문서 API가 사람이 책임지는 실제 작업 안에서 어느 자리를 맡을 수 있는가, 실패했을 때 무엇을 시스템 쪽에서 받아야 하는가입니다. 그래서 이번 체험은 Solar를 제 에이전트 하네스에 다시 올리는 일과, Document AI를 제가 계속 운영해 온 문서 파이프라인에 넣는 일을 하나의 흐름으로 진행했습니다.

업스테이지를 이번 공고에서 처음 만난 것은 아닙니다. 2024년에는 Emacs의 gptel에 Solar를 OpenAI 호환 API로 직접 연결해 상시 대화면에 두었고, Solar Pro·Mini·일본어 모델을 선택할 수 있게 설정했습니다. 번역기의 커스텀 API도 한동안 업스테이지로 두었습니다. 당시 cookbook을 별도로 저장해 두고, 자체 GPU 클러스터를 구성할 때도 한국어 모델 축의 후보로 Solar를 검토했습니다. 이후 제 작업면은 다른 모델과 도구들로 옮겨 갔습니다. 지금까지 계속 사용했다고 말하지는 않겠습니다. 다만 2025년 10월에는 업스테이지 커리어 토크 페이지를 북마크해 두었고, 이번에는 과거의 인상을 되풀이하지 않기 위해 현재 제품을 다시 제 환경에 올려 실제 작업으로 확인했습니다.

2026년 7월 30일, Pi에 기본 provider로 없던 Solar를 `agent-config` 확장으로 등록했습니다. 단지 API 요청 하나를 성공시키는 일은 아니었습니다. 하네스가 기대하는 메시지 역할, 상태 저장, 도구 호출 스키마, 스트리밍 사용량, 프롬프트 캐시와 reasoning budget의 계약을 API가 실제로 어떻게 받는지 맞춰야 했습니다. 일부 OpenAI 호환 옵션은 그대로 전달하면 거부되어 호환 블록에서 제외해야 했고, 반대로 reasoning effort와 스트리밍 usage, 캐시 토큰 보고는 동작을 확인했습니다. 모델 목록에 응답하지 않는 Solar 별칭은 별도로 등록해야 선택 가능한 상태가 되었습니다. OpenAI compatible이라는 한 줄은 출발점일 뿐, agent가 오래 사는 제품면에 들어가기 위한 계약 전체는 아니라는 것을 다시 확인했습니다.

그날 Solar Pro 3를 실제 Pi 세션의 모델로 선택해 한국어 대화와 도구 사용, 그리고 garden id로 다른 에이전트에게 메시지를 보내는 흐름까지 올려 보았습니다. 짧은 상호작용에서는 낮은 reasoning 설정이 적합했지만, 높은 설정은 대화형 작업에 과할 만큼 응답이 길어졌습니다. 더 중요한 관측은 도구 사용에 있었습니다. 다른 에이전트의 garden id를 받았을 때 처음에는 원시 세션 파일을 직접 읽는 쪽으로 갔고, 이후에야 정해 둔 citizen 조회 표면에 도달했습니다. 모델이 도구를 호출할 수 있다는 사실만으로는 충분하지 않았습니다. 어떤 객체를 어떤 정본 인터페이스로 다뤄야 하는지, 그리고 실패했을 때 파일 경로가 아니라 안전한 작업 표면으로 되돌아오게 하는 설계가 필요했습니다. 저는 이 경험을 Solar의 단순한 성공·실패 판정보다, reasoning을 작업 유형에 따라 배치하고 provider·도구·권한의 계약을 명시해야 하는 Agent 제품의 관측으로 남겼습니다. Solar Open 2는 제 계정에 호출 권한이 열리지 않아 평가하지 않았습니다.

문서는 이보다 더 오래 붙잡아 온 문제입니다. 2026년 5월 31일 스캔책 작업 저장소를 열고, 6월 2일에는 MinerU 출력으로 한국어 책을 Org와 EPUB로 다시 만드는 첫 파이프라인을 남겼습니다. 다음 날에는 깨진 본문을 전수 교정해 다시 만들었고, 6월 4일에는 페이지 경계에서 갈린 문단을 감독형으로 이어 붙이는 규칙을 넣었습니다. 이 기록이 중요한 이유는 제가 OCR 결과를 텍스트 한 번 뽑고 끝내지 않기 때문입니다. 스캔 PDF가 들어오면 구조화된 텍스트가 되고, Org가 그 계보와 편집 경계를 보존하며, 다시 EPUB·검색 색인·사람과 agent가 읽을 작업면으로 나가야 합니다.

7월 30일에는 그 흐름에 Upstage Document Parse를 넣었습니다. 이전부터 같은 한국어 책 구간에 놓아 보던 MinerU, PP-StructureV3, DeepSeek-OCR, PaddleOCR-VL, GLM-OCR의 출력과 같은 자리에 두었습니다. 첫 인상은 글자 층에서 분명했습니다. 기존 엔진들이 서로 다른 곳에서 깨뜨리던 톰슨·돌턴·슈뢰딩거·찐빵 같은 고유명사와, MinerU가 원문에 없던 한자를 만들었던 문장을 Document Parse는 함께 보존했습니다. 그러나 이 결과만으로 “가장 좋다”라고 결론내리지 않았습니다. 수식과 2단 도판이 많은 같은 책에서는 화학반응식이 equation이 아니라 heading으로 분류되고, 그림 캡션이 본문 문장 한가운데 끼어들어 reading order를 깨뜨렸습니다. 모델의 문제인지 문서 유형의 문제인지 가르기 위해 수식 없는 인문서 구간을 다시 넣었습니다. 그곳에서는 소제목, 각주, 번호 목록, 표가 안정적으로 분리됐습니다. 저는 이 결과를 품질 순위가 아니라 조판 유형에 따른 배치 규칙으로 읽었습니다.

그래서 현재의 판단은 명확합니다. 산문·보고서처럼 구조가 비교적 안정적인 문서는 Document Parse를 중심에 둘 수 있습니다. 반면 수식과 도판이 빽빽한 과학책은 기존 도구가 구조 골격을 맡고, Upstage Document 계열은 글자 층의 검수와 교정 후보를 맡는 조합이 맞습니다. 제가 필요한 것은 어느 한 모델이 모든 문서를 이기는 선언이 아니라, 문서가 달라져도 실패 양상을 알고 조합을 바꿀 수 있는 파이프라인입니다.

실패는 더 구체적인 운영 규칙으로 남겼습니다. 화살표와 개념 라벨뿐인 칸트 도식을 막대차트로 해석하면서 원문에 없는 수치가 든 표를 생성한 사례가 있었습니다. 이 경우 글자 한두 개의 오독보다 위험한 것은, 그럴듯한 숫자가 정본과 지식베이스에 들어가 나중에 출처를 잃는 일입니다. 따라서 도식이 있는 문서에서는 `chart_recognition`을 끄고, 생성된 구조나 설명은 Org 정본에 바로 넣지 않고 검수 경로를 거치게 했습니다. enhanced 모드가 도판의 영문 설명을 추가했지만 원문에는 없는 생성 텍스트였기에, 본문이 아니라 검색용 메타데이터 후보로 분리한 것도 같은 이유입니다.

Document Parse만 평가하고 멈추지 않았습니다. 같은 문서 흐름에서 Document OCR, Information Extraction, Classification을 각각 실제 통증에 붙였습니다. Document OCR은 단어별 confidence와 bounding box를 돌려 주어, 여러 엔진의 불일치만으로 찾던 오독 후보를 검수 큐로 보내는 데 더 직접적이었습니다. Information Extraction은 판권지에서 책 제목·저자·출판사뿐 아니라 기존 수작업 메타데이터에서 빠졌던 ISBN과 정확한 발행일까지 구조화했습니다. 반면 Classification은 본문·목차·찾아보기라는 쪽 유형 자체는 유용하게 분류했지만, 응답에 쪽과 그룹의 대응이 없어 본문 경계를 자동으로 결정하는 역할에는 아직 두지 않았습니다. 제품군 전체를 한 덩어리로 칭찬하는 대신, API마다 무엇을 정본 가까이에 놓고 무엇을 보조 검수로 둘지 나눠 판단한 것입니다.

업스테이지 Document AI가 HWP·HWPX를 입력으로 받는다는 점도 제가 계속 파 온 한국어 문서 환경과 만납니다. 저는 HWPX, 스캔 PDF, EPUB, Org와 오피스 산출물을 오가며 플랫폼에 묶인 문서를 다시 읽고 만들 수 있는 형태로 바꾸는 도구들을 만들어 왔습니다. 한국어 문서는 레이아웃뿐 아니라 형태소, 한자 병기, 관공서 양식, 스캔 품질 때문에 일반적인 문서 파이프라인이 조용히 무너지는 자리입니다. 이 제품군은 그 문제를 단순 OCR이 아니라 이후 agent와 검색이 소비할 수 있는 구조로 바꾸는 입구가 될 수 있다고 봅니다.

결국 제가 본 것은 Solar와 Document AI의 개별 기능 목록이 아닙니다. 문서 구조화, OCR 검증, 메타데이터 추출, 검색 색인 적재, 도구를 쓰는 agent, 그리고 사람이 최종 판단을 되찾는 작업면이 이어지는 전체입니다. 저는 이 연결을 제 환경에서 이미 만들고 고쳐 왔습니다. 업스테이지 Agent Engineering팀에서는 모델을 인상적인 데모에서 멈추지 않고, 고객의 문서·도구·권한·결정 안에서 오래 작동하는 제품으로 옮기는 일을 하고 싶습니다. 제품 평가를 점수표로 끝내지 않고, 실패를 재현 가능한 운영 규칙과 더 나은 agent 경험으로 돌려주는 엔지니어가 되겠습니다.
