## 문항 1 — 업스테이지 제품 체험 평가 (필수 · 10,000자)
# 2702자 (공백 포함)

저는 모델 제품을 응답 한 번의 성능으로만 평가하지 않습니다. 실제 조직의 문서·데이터·도구와 만났을 때 모델이 무엇을 읽고, 어디까지 행동하며, 실패와 판단을 누구에게 돌려줄 수 있는지를 함께 봅니다. 그래서 이번 체험도 Solar를 제 에이전트 하네스에 넣는 일과, Document AI를 실제 문서 파이프라인에 놓는 일을 한 흐름으로 진행했습니다.

Solar Open 2는 현재 제 계정에 호출 권한이 없어 평가 대상에서 제외했습니다. 대신 공개된 Solar Pro 3를 Pi에 직접 붙였습니다. 기본 provider가 없어서 `agent-config/pi-extensions/upstage-provider.ts`로 `api.upstage.ai/v1`을 OpenAI-compatible provider로 등록했습니다. OpenAI 호환이라는 표기만으로 agent가 그대로 올라가지는 않았습니다. `store`, developer role, strict tool schema, reasoning effort, streaming usage, prompt cache처럼 하네스가 기대하는 런타임 계약을 하나씩 대조해야 했습니다. 모델 호출을 성공시키는 것과, 다른 도구·세션·사람의 판단 사이에서 오래 쓰는 실행면에 넣는 것은 다른 일이라는 점을 이 통합에서 확인했습니다.

이 경험은 업스테이지가 제공하는 개발자 표면을 읽으면서 더 선명해졌습니다. 공식 문서는 Claude Code와 Hermes Agent를 Solar provider로 등록하는 통합 경로와, 코딩 에이전트가 읽을 원문 API 문서를 함께 제공합니다. 제가 손으로 provider 경계를 확인한 일과 회사가 제품으로 열어 둔 길이 같은 질문을 향합니다. 중요한 것은 원클릭 연결 자체가 아니라, 서로 다른 하네스에서도 모델·도구·기억· 권한의 소유 경계를 잃지 않으며 통합을 운영하는 일이라고 봅니다. Solar Open 2의 긴 문맥 지향도 기술보고서로 읽었지만, 접근하지 못한 모델의 성능을 제 경험인 양 말하지는 않겠습니다.

Document Parse는 제가 운영해 온 스캔책 파이프라인의 기존 OCR 비교축에 추가했습니다. 기존 기록은 MinerU, PP-StructureV3, DeepSeek-OCR, PaddleOCR-VL의 모델/도구 모드, GLM-OCR을 같은 한국어 책 구간에서 비교한 것이고, 이번에는 최무영 《물리학 강의》의 동일 구간에 Upstage Document Parse를 놓았습니다. 이번 직접 대조는 MinerU 중심이며 gold 대조 벤치마크는 아닙니다. 따라서 아래 판단은 제품의 절대 순위가 아니라, 제가 실제로 운영하는 파이프라인에 무엇을 어떻게 배치할지에 대한 운용 판정입니다.

글자 층에서는 고유명사가 강했습니다. 기존 엔진들이 서로 다른 자리에서 깨뜨렸던 톰슨·돌턴· 슈뢰딩거·찐빵을 이번 출력은 함께 보존했고, MinerU가 이 구간에서 만든 한자 환각도 없었습니다. 반면 구조 층은 문서 유형에 민감했습니다. 수식과 2단 도판이 밀집한 구간에서는 화학반응식이 `equation`이 아니라 `heading1`로 분류되고, 그림 캡션이 본문 문장 한가운데를 갈라 reading order가 무너졌습니다. 수식 없는 인문서 구간에서는 소제목·각주·목록·표가 안정적으로 분리됐습니다. 그래서 산문 문서는 Document Parse를 중심으로 두되, 수식·도판이 많은 과학책은 기존 도구가 구조 골격을 맡고 Upstage OCR이 글자 검수에 들어가는 조합이 맞다고 판단했습니다.

실패도 운영 규칙으로 남겼습니다. 화살표와 개념 라벨뿐인 칸트 도식을 막대차트로 오인해 원문에 없는 수치가 든 표를 생성한 사례가 있었습니다. 도식이 있는 문서에서는 `chart_recognition`을 끄고, 생성 결과는 정본에 바로 넣지 않고 검수 경로를 지나게 해야 합니다. 없는 숫자가 지식베이스에 섞이는 일은 글자 한두 개의 오독보다 훨씬 되돌리기 어렵기 때문입니다.

같은 문서 흐름에서 Document OCR, Information Extraction, Classification도 각각의 자리를 확인했습니다. OCR의 단어별 confidence와 bounding box는 여러 엔진의 불일치로 찾던 오독 후보를 검수 큐로 보내는 데 맞았고, Information Extraction은 판권지에서 누락된 ISBN까지 메타데이터로 채웠습니다. Classification은 쪽 유형 자체는 유용했지만 쪽과 그룹의 대응을 얻지 못해 본문·찾아보기 경계를 자동으로 정하는 용도는 보류했습니다. 제품군을 한 덩어리로 칭찬하는 대신, 문서 유형과 작업 단계에 따라 어느 API를 어느 검증 경계에 둘지 나누는 것이 더 실무적인 사용법이라고 봅니다.

이 경험을 통해 제가 보고 있는 제품의 자리가 분명해졌습니다. Document AI는 OCR 정확도 순위가 아니라, 비정형 문서를 모델과 agent가 읽고 행동할 수 있는 구조로 바꾸는 입구입니다. 그 뒤에는 문서 유형별 평가, 검색 입력 품질, 근거를 남기는 장기 실행 workflow, 그리고 사람이 예외와 최종 판단을 소유하는 작업면이 이어져야 합니다. 저는 문서 구조화 → OCR 검증 → Org/EPUB·검색 색인 적재를 역할이 분리된 agent workflow로 연결해 왔습니다. 업스테이지에서라면 모델의 능력을 실제 업무의 문서·도구·결정으로 옮기는 이 경계 — 제품 평가를 고객의 운영 규칙과 재현 가능한 agent 경험으로 바꾸는 일 — 을 함께 만들고 싶습니다.

## 문항 2 — 지원 분야와 관련된 업무 경험 (필수 · 1,000자)
# 764자 (공백 포함)

제가 해 온 일은 에이전트를 인상적인 데모가 아니라 매일 쓰는 도구로 굴리는 것이었습니다.

운영. AI 에이전트 하네스를 직접 만들어 상시 운영합니다. 상류가 깨질 때마다 그것을 운영 규칙으로 번역했고, 스킬 단일 정본 하나를 여러 하네스에 배포해 한 곳을 고치면 전부가 따라오게 했습니다.

워크플로와 프로토콜. 서로 다른 하네스가 상대의 대화기록·인증·런타임을 소유하지 않고 식별자로 서로를 주소하는 협업 기층을 설계해 공개했습니다. 설계 주장에 그치지 않았다는 근거는 제3자입니다. 만난 적 없는 개발자가 다른 백엔드를 붙이겠다며, 제가 확장점이라고 말한 바로 그 자리를 찾아 들어와 11개 파일 885줄을 기여했습니다.

문서와 검색. 공용 GPU도 임베딩 기반도 없던 자리에 클러스터와 데이터 파이프라인을 깔고 사내 문서 검색을 직접 서빙한 뒤, 담당자에게 붙는 도메인 에이전트를 세웠습니다. 개인 작업에서는 HWPX·스캔 문서를 Org와 검색 색인으로 연결하는 파이프라인을 운영했고, 이번 Upstage Document Parse 평가도 그 워크플로 위에서 수행했습니다. Document AI가 본진인 회사라 이 축이 가장 가깝습니다.

경계도 밝힙니다. 관측 설계는 하네스 로그와 세션 축 수준이지 OpenTelemetry 급이 아닙니다. 모델 서빙·경량화 실적이 없고 VLM은 얇습니다. Rust는 제 축이 아닙니다.
