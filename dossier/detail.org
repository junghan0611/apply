* 이 문서를 읽는 법

이 문서는 두 PDF(역량·성과 기술서 / 포트폴리오)에서 판면상 덜어낸 구현 세부·파일 경로·재현 명령·실패 사례·설계 판단·검증 URL을 회수한 *원문입니다*. 세 갈래로 씁니다.

1. *사람(채용 검토자):* 프로젝트마다 「검증 질문」과 「소유·비소유 경계」만 읽어도 깊이와 정직성을 판정할 수 있습니다.
2. *에이전트(자동 탐색):* 공개 저장소 URL·파일 경로·명령이 있어 실제 코드로 내려가 주장을 검증할 수 있습니다.
3. *T인터뷰(라이브 코딩, Claude Code):* 「재현 명령」과 「핵심 파일」은 그 자리에서 열어 실행할 진입점입니다.

*확인 경로는 세 라벨로 표시합니다.* =[공개]= 는 링크를 열어 지금 확인 가능한 것, =[사내]= 는 회사 안에서 수행해 외부에서 열 수 없는 것, =[운영 기록]= 은 아래 시간축 관측소에서 날짜·시각·커밋 단위로 제시할 수 있는 것입니다. 서열이 아니고 배타적이지도 않아 =[사내]= 와 =[운영 기록]= 이 함께 붙습니다. 원시 고객 식별자·자격증명·회사 실명은 이 문서에 없습니다.

* 관측 도구 — 이 문서를 검증하는 방법

*이 절이 이 문서에서 가장 중요합니다.* 포트폴리오의 서사는 누구나 쓸 수 있습니다. 그 서사가 실제로 지나온 시간축 위에 있는지를 확인할 수 있어야 검증이 됩니다. 그래서 주장을 쓰기 전에 *관측 도구를 먼저 만들었습니다.*

** 시간축 관측소 [공개 도구 · 사적 데이터]

제 org-agenda·저널·노트·커밋·시간기록을 *하나의 KST 축 위에 정규화하는 수집기* 를 씁니다 [cite:@repo-agent-config]. 이력서용으로 고른 최고작이 아니라, 그 기간에 실제로 무엇이 남았는지를 그대로 엽니다.

| 깊이 | 무엇이 보이나 | 기록의 성격 |
|------+---------------+-------------|
| 0 | 하루의 시간 배분 — 수면·가족·독서·작업 | 의도적 기록(수기 export) |
| 1 | 그날 무엇을 적었나 (저널 헤딩) | 의도적 기록 |
| 2 | 에이전트가 무엇을 했나 (agenda 스탬프) | 산출물의 잔여물 |
| 3 | 커밋 하나하나, 노트 하나하나 | 산출물의 잔여물 |

*깊이 0·1은 의도이고 2·3은 잔여물입니다.* 잔여물만 읽는 도구는 무엇이 생산됐는지는 말해도 그것을 생산한 시간은 말하지 못합니다. 이 문서의 =[운영 기록]= 라벨은 전부 이 축에서 나옵니다.

| =events_sha256= | =095e8e3b60abfb6458021218afa57863e3e0bdc5768313f1cfcd3c287c3ab09f= |
| =code_sha256= | =a847831b2edd82946279753e1ec5b3a077a50d83a01e2dd50308a99ffb6f3ca4= |
| 수집기 | collector 0.7.0, schema 1 |
| 모집단 | 이벤트 29,108 · 엔티티 24,207 |

소스 상태: =git= ok(10,017) · =agenda= ok(3,820) · =journal= ok(1,355) · =note= *partial* (5,516 수용 / 25 거부 — 중복 식별자 8, 파싱 불가 17) · =timelog= *stale* (8,400, 2026-07-13까지 도달).

*지문이 둘인 이유가 중요합니다.* =events_sha256= 은 파일의 정확한 바이트를 덮고, =content_sha256= 은 각 이벤트에서 «이 디스크의 어디서 읽었나»(provenance)를 뺀 관측 내용만 덮습니다. 제 agenda는 역방향 datetree라 *스탬프 하나만 찍혀도 옛 줄이 전부 밀립니다* — 관측이 하나도 안 바뀐 오후에 바이트 해시가 세 번 달라진 적이 있습니다. 그래서 *인용은 =content_sha256= 으로 합니다.* 그것을 못 박지 않으면 인용은 다음 스탬프에 죽습니다.

** 이 지문이 증명하지 않는 것

*정직하게 적습니다. 이 경계를 넘어서 주장하지 않습니다.*

- *해시는 «이 코드가 실제로 돌았음»을 증명하지 않습니다.* 바이트와 그 해시는 누구나 함께 만들 수 있습니다. 지문이 하는 일은 주장된 파생 경로를 *기록* 하고, 그 기록이 가리키는 내용의 *동일성을 확인해 바꿔치기를 잡는* 것까지입니다.
- *소스의 진실성도 완전성도 증명하지 않습니다.* 이 축은 이 기기가 말해 준 것을 적었을 뿐입니다.
- *외부 독립 확인 가능성은 사건의 «공개 도달성»에 달려 있습니다.* 공개 remote에 도달한 커밋과 공개 가든으로 export된 기록은 외부에서 확인됩니다. 비공개 저장소·푸시되지 않은 ref·export되지 않은 기록은 재구성되지 않습니다. *«깊이 3은 누구나 검증 가능»도 «내 기록은 전부 비공개»도 둘 다 거짓입니다.*
- *깊이 0은 폰에서 손으로 export한 1인칭 기록입니다.* 외부에서 원본을 재구성할 길이 없습니다. 확인 가능한 것은 파생의 일관성뿐입니다.
- =timelog= 이 =stale= 이고 =note= 가 =partial= 이므로, *이 데이터로 무언가의 «부재»를 주장하지 않습니다.* 검색 결과가 없는 것과 사건이 없는 것은 다릅니다. 관측되지 않은 것과 공개되지 않은 것도 다릅니다.

*«ok»를 함부로 쓰지 않는 것이 이 도구의 설계 원칙입니다.* 0건은 =ok= 가 아니라 =empty= 이고, 깊이 0이 다른 소스가 증언하는 날을 못 덮으면 =stale= 입니다. 마운트가 빠진 디스크에서 «정상이며 비어 있음»으로 보고되는 것이 가장 위험한 실패이기 때문입니다.

* 프로젝트 1 — AX 전환 인프라와 도메인 에이전트 [사내]

*검증 질문.* /기존 운영 시스템을 하나도 바꾸지 않고 증거 경로만 냈다는 것을, 코드를 열지 않고 어떻게 확인할 수 있는가?/ → 답은 두 가지입니다. (a) 착수 첫날의 커밋 순서가 «계약이 기능보다 먼저»를 보여 줍니다. (b) 같은 추론 방식의 공개 실험체가 있어 사내 코드 없이도 설계를 열어볼 수 있습니다.

** 1단계 — 기반 구축 (2025-06 ~ 2025-09)

입사 시점에 공용 GPU도, 임베딩 기반도, 업무 데이터를 한곳으로 모으는 파이프라인도 없었습니다.

- *GPU 클러스터* — RTX 5080 3대, NixOS, 10G 네트워크, Docker 서비스 17개.
- *계층형 에이전트 시스템* — n8n 워크플로 위에 pgvector 문서 임베딩을 물리고, 임베딩·리랭킹 단계를 빌리지 않고 직접 서빙했습니다 [cite:@pgvector].
- *데이터 파이프라인* — Airbyte 커넥터로 상담·문서·이슈 시스템을 PostgreSQL JSONB 한 곳으로 수집.
- *사내 포털* — Cloudflare Zero Trust 뒤에 배치.
- *임베딩·리랭킹 직접 서빙* — 모델 파인튜닝이 아니라 GPU·컨테이너·네트워크·인증 경계를 다뤘습니다.

*이 단계가 공고 주요 업무 ①(AX 전환을 위한 시스템 인프라 구축·관리)에 정확히 대응합니다.* RAG를 데모로 끝내지 않고 이미 돌던 낡은 사내 시스템에 붙여 실제 업무 데이터까지 밀었습니다.

** 2단계 — 도메인 워크벤치 (2026-05 ~ 현재)

*구조(텍스트).* 업무 원천(디바이스 로그·상담·사내 문서·클라우드 이벤트) → 읽기 전용 수집 → 정규화된 시간축·집계 계층 → 도메인 담당자의 질의 표면. *변경 경로는 없습니다.*

** 재현 명령 — 공개 아날로그로 설계를 여는 법

사내 코드는 열 수 없지만 *추론 방식 자체는 공개 저장소에서 실행됩니다* [cite:@repo-abductcli].

#+begin_src shell
git clone https://github.com/junghan0611/abductcli && cd abductcli
clj -M:run pipeline                        # 전체 귀추 파이프라인
clj -M:run import data/superstore.csv      # 원자료 적재
clj -M:run detect --grain category         # 기준선과 다른 신호 검출
clj -M:run suggest-signals --anomaly anom-001   # 잔차를 다음 가설로
#+end_src

*숫자의 정직성 4단계* — 이 순서가 두 사내 워크벤치의 공통 골격입니다. ① 모든 숫자의 단위·기간·포함 정책을 먼저 고정 ② 근거를 개별 원본 id까지 역추적 가능하게 ③ 기준선과 *다른* 신호를 잡기 ④ 설명되지 않고 남은 *잔차를 다음 사이클의 가설로* 넘기기.

** 소유·비소유 경계

- *소유:* 두 단계의 설계·구현·운영, 운영팀 요구의 계약 번역, 개인정보·권한·원천 시스템 경계 합의.
- *비소유:* 원천 운영 시스템 자체. 이 프로젝트는 그것을 *바꾸지 않는 것* 이 설계입니다.
- *자격증명은 에이전트가 취급하지 않습니다* — 사람이 직접 다룹니다. 세션별로 분리해 관리합니다.
- *변경·실행 경로 금지* — freeze/delete/transfer/reset 계열 경로는 워크벤치에 없습니다.
- *원시 개인정보는 표준입력(=-=) 경계로만 흐릅니다.* 문서·세션·커밋에 남기지 않습니다.
- *덤프를 쌓지 않습니다.* 저장하는 순간 그 덤프가 또 하나의 거짓말이 되므로, 살아 있는 원본에서 읽습니다.

** 실패와 교정

- *«단일 SSO가 전부 커버한다»는 가정을 폐기했습니다.* 실제로는 콘솔마다 세션 경계가 달라, 세션별 자격 분리로 재설계했습니다.
- *2,749개 테이블 전수 매트릭스 조사를 금지했습니다.* 탐색 범위를 seam 단위 카탈로그 crosswalk로 한정합니다 — 전수 조사는 답이 아니라 소음을 만듭니다.
- *«얼마나»와 «언제»를 한 도구에 넣지 않았습니다.* 두 질문의 시간 모델이 달라 하나로 합치면 둘 다 부정확해집니다. 그래서 워크벤치가 둘입니다.

** 인계 지점

운영팀의 반복 고통 청취 → 요구를 계약으로 번역 → 경계 합의 → 워크벤치 제공 → 피드백을 다시 데이터·문서·이슈로 되돌리는 루프. 상담 분석 채널의 실제 대화를 ground truth로 회수해 집계 정의를 교정합니다.

- *증상:* 두 판 점프 후 응답 지연이 급증하고 처리 상태에 멈춘 세션이 누적됐습니다.

- *가설 배제:* 클린 부팅에서도 재현 → 운영자 설정 오류가 아님.
- *원인 가설:* 콜드 영속 플러그인 레지스트리와 자동 수정 도구의 충돌 → 레지스트리 재구축이 활성 플러그인을 줄임 → 첫 인입이 hot path 한복판에서 의존성 설치를 유발.
- *롤백 타깃 선택(핵심):* 한 단계 아래가 아니라, *이미지 생성이 기존 인증 경로로 라우팅되는 마지막 정상 판* 으로. «최신을 고집하지 않음»과 «아무 데나 되돌림»은 다릅니다.
- *복구 검증:* 정상 부팅·유휴 상태를 회복하고 정체 세션 진단이 사라진 것을 확인했습니다.
- *하드닝 후:* 의존성 스테이징을 hot path 밖으로 옮기고 정체 세션 누적을 줄였습니다.

| Claude Code | 세션 시작 훅이 메타세션으로 등록, 우편함 | mailbox-citizen |
| Antigravity | 호출 전 훅이 네이티브 대화에 바인딩 | native-push citizen |

*Codex는 이 표에 없습니다.* 외부 MCP 호스트로 브리지를 소비해 기존 시민에게 *전달할 수는 있지만* 주소를 가진 시민도 회신 레일도 아직 아닙니다. 할 수 있는 것과 아직 못 하는 것을 같은 칸에 적지 않습니다.

*전달 동사는 하나입니다.* 대상의 garden id를 주면 기층이 상대의 생존을 자기 레일에서 직접 확인하고 네 경로 중 하나를 고릅니다 — 컨트롤 소켓 전송, 휴면 세션 재개, 우편함 적재, 네이티브 직접 주입. *살아 있음은 저장하지 않고 매번 계산합니다. 저장된 생존 표시는 거짓말이기 때문입니다.*

*경계.* 현재 ACP 백엔드는 Claude 하나입니다 [cite:@acp-spec;@claude-code]. 나머지 하네스는 ACP가 아니라 각자의 공식 표면으로 붙습니다 [cite:@openai-codex]. 이 기층은 *이미 식별된* 시민에게 전달할 뿐 새 분신을 만들지 않습니다 — 그 능력은 별개이고 아직 열지 않았습니다.

** 제3자의 행동이 드러낸 것 [공개]

*한 번도 만난 적 없는 개발자가 Snowflake Cortex Code ACP 백엔드를 들고 왔습니다* — 11개 파일, +885줄 [cite:@pr-entwurf-40]. 제가 한 번도 써 본 적 없는 기업용 에이전트 런타임입니다.

*그리고 이 기여가 0.12.0 전환 과정의 설계 후퇴를 짚어 냈습니다.* 0.11.0에는 백엔드 어댑터 패턴(=AcpBackendAdapter= 인터페이스와 백엔드 레지스트리)이 있었고 기여자는 거기에 cortex를 네 번째로 끼웠습니다. 그사이 비대해진 브리지를 통째로 버리고 Claude 단선으로 다시 짓는 과정에서 *그 추상화를 한때 함께 걷어냈습니다.* 단일 백엔드의 코드 품질은 올랐지만 백엔드 추가 레일은 0.11.0보다 뒤로 갔습니다.

*그래서 순서를 뒤집었습니다.* =AcpBackendAdapter= 인터페이스를 다시 깔고 Claude를 그 첫 구현으로 리팩터하는 작업은 현재 0.12 계열에 반영돼 있습니다. cortex를 두 번째 구현으로 받는 작업은 0.13.0에 둡니다 — «두 개가 돼야 패턴이 산다». 이 결정과 *후퇴가 있었다는 사실 자체* 를 공개 로드맵에 적어 두었습니다 [cite:@issue-entwurf-48]. cortex 수용 때 봉합할 지점은 7개로 특정돼 있습니다(실행 해석 · 오버레이 · 세션 메타 · 모델 라우팅 · 모델 강제 · 설정 서명 · 게이트).

** forge-config — 판단이 남는 공유 작업면

*운영 루프.* 도메인 담당자가 봇과 대화 → 요구·버그 감지 → 라벨과 소스 컨텍스트를 붙여 셀프호스팅 Forgejo 이슈 생성 [cite:@forgejo] → 봇이 웹훅으로 깨어남 → 읽기 전용 1차 검토 요청 → 현실성·위험·범위·우선순위 반환 → 검토 기록과 분류 종료 → *사람이* 정렬된 백로그를 보고 구현.

*상태 권위(설계 핵심).* 템플릿 마커가 스키마·리포트 id·세션 키·이슈 갱신 시각·수명주기 라벨·모델·설정 커밋을 기록합니다. 목적은 하나 — *세션 기억과 웹훅 재생이 현재 Forge 상태를 절대 이기지 못하게.* 에이전트의 기억보다 durable store가 권위입니다.

*하지 않기로 한 것(non-goal).* 자동 코딩 공장 아님 · 운영 대시보드 제품 아님 · 무엇을 구현할지 정하는 사람의 일을 대체하지 않음. 봇은 *dispatcher/recorder이지 implementer가 아닙니다.* BMAD류 워크플로와 같은 문제층을 다루지만 직접 사용했다고 쓰지 않습니다 [cite:@bmad-method].

*실증 착지.* 제한된 auto-fix 레인이 실제 저장소에서 동작했고, *재생·멱등성 스모크에서 리포트 중복이 0* 이었습니다. 후속 라운드에서 작업공간 경계 가드, 검색 무매치를 치명적이지 않은 sweep 사례로 처리, 수정 후 회귀 통과까지 갔습니다 [운영 기록].

*착수 첫날(2026-05-27)에 스캐폴드 → 최소 명령 네 개 → 설계 결정 6건 확정 → 다중 프로파일 → 이슈 생성 동사까지 갔습니다* [운영 기록]. *«무엇을 만들지»가 아니라 «무엇을 하지 않을지»를 먼저 닫아서 하루에 형태가 잡혔습니다.*

** 핵심 판단

*① 붙이는 설계가 아니라 갈아 끼울 수 있게 자르는 설계.* 배포 토폴로지와 도메인 계약을 분리해, 장치와 앱이 배포 방식과 무관하게 같은 상태 의미를 유지하게 했습니다. 경계에서 상태나 프로토콜이 조금씩 어긋나면 각 부분은 정상이어도 *제품 전체가 조용히 실패합니다.*

** 배경 — 이 축의 첫 사례

대형 터치 디스플레이용 Linux 플랫폼(공동창업 2013–2017, 양산): Yocto 기반 BSP [cite:@yocto], 다중 사용자 OS. *«펌웨어에서 제품까지»의 첫 사례이고, 지금 축의 원형입니다.*

*사내 R&D(durable-iot-migrate) [사내]:* IoT 자동화 레시피 이관을 durable execution으로 재정의하는 설계 제안 — Temporal·Saga·의미 보존 검증·감사 가능한 저장 [cite:@temporal-durable;@saga-pattern]. Clojure Expr IR로 플랫폼 차이를 어댑터 경계로 격리. *제안·설계 단계입니다.*

** 소유·비소유 경계

- *소유:* 펌웨어·서버·앱·제품 통합의 세로축 전체, 전환 전략, 프로토콜 경계 설계.
- *비소유:* 넘겨받기 전의 원 설계. *이 프로젝트는 남이 시작한 것을 받아 닫은 사례입니다.*
- *비소유:* 벤더 SDK, AOSP, Matter 명세 자체.

** 인계 지점

*이 축은 인계로 열려서 인계로 닫힙니다.* 급히 넘겨받은 시스템을 이해 가능한 계약으로 바꾸어 양산까지 보냈고, 빌드 환경과 프로토콜 경계를 다시 문서로 남겨 장치·서버·앱 담당자가 같은 계약을 확인하게 했습니다. 온디바이스 허브는 아예 공개 저장소로 두어 설계 판단을 열어 두었습니다. *받는 능력과 남기는 능력이 한 축에서 닫힙니다* — 조직에서 사람이 바뀌어도 시스템이 이어지려면 두 쪽이 다 필요합니다.

* 조직이 이어받는 방법 — 문서와 도구

*문서는 사후 보고서가 아니라 실행 인터페이스입니다.* 사람과 에이전트가 같이 읽는 계약서로 다룹니다. 역할을 나눴습니다 — 오래 유지할 원칙과 불변식은 =AGENTS.md=, 하중을 받는 낱말을 한 번만 정의하는 =VOCABULARY.md=, 세션 사이 인계는 =NEXT.md=, 에이전트가 자기 작업을 스스로 남기는 =botlog=.

*그 계약서에는 실패도 적습니다.* 제 공개 저장소의 =AGENTS.md= 에는 «커밋 수를 저장소 루트 전체 순회로 세지 말 것 — 같은 저장소의 클론이 중복 계수된다»가 규칙으로 박혀 있습니다. 실제로 그 함정에 빠져 90일 수치가 부풀었던 사고가 있었고, 지우는 대신 문서에 박아 뒀습니다. *다음 에이전트를 구하는 것은 잘 정리된 성공담이 아니라 기록된 실패입니다.*

*어떤 형식의 문서든 터미널에서 변환·배포합니다.* 위의 모든 것은 «문서가 평문 텍스트가 될 수 있다»를 전제합니다. *한국에서는 대개 안 됩니다.* 그래서 =memex-kb= 를 만들었습니다 [cite:@repo-memex-kb;@note-memex-kb] (120 커밋 / 33 작업일) — 한글 워드프로세서 포맷을 위한 =hwpx2org=, 스캔된 종이를 비전 전사로 넘기는 =scanpdf2org= [cite:@note-memex-ocr], =epub2org= 와 =html2epub=, 오피스 포맷 왕복을 맡는 =org2odtdoc=, 한국어 산문 린팅 =textlint-ko=, 그리고 실제로 예산을 결정하는 문서들을 위한 제안서 파이프라인 [cite:@note-memex-proposal]. Org-mode를 메타 문서로 두고 전부 그리로 통과시킵니다 [cite:@note-org-ssot].

*이 제출본 자체가 그 방식의 실증입니다.*

#+begin_src shell
cd dossier
./run.sh check       # 도구·폰트 확인
./run.sh all         # competency + portfolio + detail 빌드
./run.sh verify      # 페이지 수·판형·한글 텍스트·캡션 연번·프롬프트 미누출
./run.sh package     # allowlist ZIP 조립 + 절대경로 누출 검사
#+end_src

조판 클래스·한글 엔진·활자까지 =flake.nix= 에 빌드 입력으로 고정해, 받는 쪽이 같은 소스에서 같은 문서를 다시 만들 수 있습니다.

*온보딩은 자료 제공이 아니라 피드백 루프입니다.* 가이드와 데모에서 끝내지 않고 사용 중 나온 질문과 실패를 다시 도구·문서·이슈에 반영합니다. 공개 디지털 가든 2,200여 페이지, org-mode 노트 3,500여 건, 서지 8,200여 건, 1,500일 넘게 이어 온 매일 저널, 40여 개의 에이전트 스킬이 같은 규칙 위에서 돕니다 [cite:@live-garden;@live-agenda-stats]. *이 숫자들이 의미 있는 것은 크기 때문이 아니라 공개돼 있고 지금 확인 가능하며 매일 갱신되기 때문입니다.*

* 정직한 경계

- Java/Spring 직접 경험을 Go/Clojure 경험으로 바꾸어 쓰지 않습니다.
- BMAD 사용 경험이 없습니다 — 같은 문제층의 독립 구현(forge-config)과의 차이를 밝힙니다 [cite:@bmad-method].
- Tailwind 직접 경험이 없습니다 — React/Preact/Lit + 디자인 토큰으로 대체했습니다.
- 파인튜닝(LoRA) 중심이 아닙니다 — 임베딩 서빙·리랭킹·검색 품질·프롬프트 설계가 강점축입니다.
- OpenClaw는 상류 소프트웨어입니다 — 제 것은 그 위의 운영층·기억 계층·개발 루프입니다.
- =entwurf= 의 ACP 백엔드는 현재 Claude 하나입니다. «모든 하네스를 ACP로 연결»이 아닙니다.
- Codex는 아직 시민이 아닙니다. 전달은 되지만 주소도 회신 레일도 없습니다.
- A2A·A2UI는 실험·부분 구현 단계이고, =dream= 축은 미구현입니다.
- 교육: 정규 교육과정 운영보다 가이드·데모·온보딩·인계·후속 지원 중심입니다.
- 사내 코드·식별 가능한 운영 데이터·원시 개인정보·회사 실명은 이 문서에 없습니다.
